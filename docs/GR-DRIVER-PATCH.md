# Экспериментальный GR-патч драйвера 616.92

Это отдельный Windows-эксперимент поверх обязательного UEFI-анлока. Он не
меняет `src/unlock_v2.c`, две release render-маски или эталонный EFI-бинарник.
Цель — проверить перенос трёх CPU-side RM изменений из закрытого Linux-драйвера
610.43.02, а не объявить заранее, что CMP 70HX имеет скрытую конфигурацию RTX.

## Статическое соответствие

Официальный `NVIDIA-Linux-x86_64-610.43.02.run` проверен по SHA-256
`3034A054BB4CDF7752FF8DC272564CB105513804BFF53538945901B16CA77463`.
Извлечённый `nv-kernel.o_binary` имеет MD5
`203B7F999395D22E041F6ED50E0D5646` и SHA-256
`AF6DBEEBE6B7D4D5EA63FA954796DC78DE69CFAA754922A3425F62DAB108B859`.
Драйвер не устанавливался: сравнение выполнено статически на извлечённом
объекте. Эталонные Linux before/after bytes взяты из опубликованного
[`patch_gr_unlock.py`](https://github.com/Icyoung/cmpunlocker/blob/master/tools/gr_unlock/patch_gr_unlock.py).

Сопоставление сделано по CFG, константам и потребителям свойства, а не по
одинаковому смещению:

| Linux 610.43.02 | Windows 616.92 RVA | Признаки соответствия | Изменение |
|---|---:|---|---|
| `_nv029797rm` | `0x5AA210` | длинная последовательность property reads, `0x4B0`, совпадающие поля/ветви | ранний `pGpu+0x4410 |= 0x1000` через code cave |
| `_nv032289rm` | `0x37FB20` | два alloc по `0x18`, поле `0x610=0x10`, тот же GR init CFG и error path | ветвь в false/GR-enabled путь (`JNE` удалён) |
| `_nv031940rm` | `0xA2C7F0` | `0x600/0x200`, `0xD334DF00`, topology/GPC loop | predicate всегда возвращает `1` |

Ранее замеченный блок RVA `0x95AC10` (файловое смещение `0x95A410`) — другой
агрегатор property-флагов. Он не совпадает с тремя Linux-функциями и не
патчится.

В Windows поле Linux `pGpu+0x4360` соответствует `pGpu+0x4410`: это видно в
семантически совпавшем topology-предикате. Поэтому перенос буквального Linux-
смещения был бы ошибкой.

Windows-изменения привязаны одновременно к allowlist-хэшу, исходным bytes и
уникальной сигнатуре функции:

| Участок | Файловое смещение | Before | After |
|---|---:|---|---|
| property entry | `0x5A9A10` | `48 89 5C 24 10` | `E9 72 3C 74 00` |
| code cave | `0xCED687` | 20 × `CC` | сохранение prologue; `OR [RCX+4410],1000`; возврат |
| GR path branch | `0x37F3BC` | `75 14` | `90 90` |
| GR-present predicate | `0xA2BFF0` | `48 89 5C 24 18` | `B0 01 C3 90 90` |

Code cave имеет RVA `0xCEDE87`; оба относительных перехода проверены по RVA.
Для ветви `_nv032289rm` Windows использует обратную полярность условия по
сравнению с Linux-патчем, поэтому здесь удаляется `JNE`, а не копируются Linux-
bytes буквально.

## Fail-closed инструменты

Поддерживаются только два заранее проверенных входа 616.92:

| Профиль | SHA-256 | Размер |
|---|---|---:|
| чистый официальный | `85753A7DDBC8D44C1ECC370BF62B5C68C05022A6D7192034186C0BA93C316BA2` | 113949416 |
| после текущего NVIDIA-patcher | `1F0D932DCE22CE14AB1ED22B7A1F28B616A654783688BEC57D52D8CA83DE7DC2` | 113939360 |

Чистый файл извлечён из официального установщика 616.92 с SHA-256
`61F117423E8AEB5A966325030DFCD5379912990119A8E7F40D78DD6513B58B6A`.
Оба профиля имеют file version `32.0.16.1692`, PE32+ AMD64 и одинаковую
геометрию `.text` (RVA `0x1000`, raw offset `0x800`). Runtime-проверка текущего
стенда показывает `GSP Firmware Version: N/A`; это наблюдение не переносится
автоматически на другую машину.

Аудит:

```powershell
powershell -ExecutionPolicy Bypass -File out\gr-driver-audit.ps1 `
  -DriverPath C:\staging\nvlddmkm.sys
```

Аудит всегда печатает `observed variant` по фактическим bytes (`R0/Stock`,
`R1/Property`, `R2/Predicates` или `R3/Full`). Это не ослабляет fail-closed
правило: неизвестный после упаковки/подписи хэш можно распознать для отчёта, но
нельзя использовать как вход для нового патча.

Создание новой копии (никогда не in-place):

```powershell
powershell -ExecutionPolicy Bypass -File out\gr-driver-patch.ps1 `
  -DriverPath C:\staging\nvlddmkm.sys -Variant Property -OutputDir C:\staging\R1
```

Допустимые варианты:

- `Property` — только ранняя установка property bit `0x1000`;
- `Predicates` — только два GR-предиката;
- `Full` — все три изменения.

Скрипт отказывает при неизвестном хэше/размере/версии, неоднозначной сигнатуре,
изменённых или уже пропатченных bytes. `Force` отсутствует. Рядом с новой
копией создаётся JSON с исходным и новым SHA-256, вариантом, смещениями и
before/after bytes. Скрипт не устанавливает драйвер и не меняет DriverStore.
После byte patch исходная Authenticode-подпись недействительна; упаковка и
подписание остаются во внешнем NVIDIA-patcher-процессе. `.sys`, сертификаты и
готовые пакеты в git не добавляются.

|---|---|
| R0 | текущий UEFI + текущий NVIDIA-patcher 616.92 |

### Результаты 2026-10-11

| Прогон | Загрузка/API | Cyberpunk 2077, медиана | Доказательство |
|---|---|---:|---|
| R0 | без Code 43 | 52,056 fps (3 прогона) | `usb-log-gr-r0-20261011.txt`, PASS |
| R1 | без Code 43 | 51,637 fps (6 прогонов) | USB-журнал не сохранён; для полной матрицы загрузку нужно повторить |
| R2 | без Code 43 | 51,886 fps (3 прогона) | `usb-log-gr-r2-20261011.txt`, PASS |
| R3 | без Code 43; CUDA, D3D и Vulkan работают | 52,057 fps (3 прогона) | `usb-log-gr-r3-20261011.txt`, PASS |

Раздельные изменения R1/R2 не дали положительного эффекта: обе медианы ниже
R0 и находятся в обычном диапазоне 51,4–52,2 fps. Для R3 сохранён установленный
`nvlddmkm.sys`: 113938808 байт, SHA-256
`1604506C43751AB175CF0DC834CF2C7319D018CD58EE4B6CC76B8076D1FB24E0`;
аудит определяет его как `R3/Full`. После reboot UEFI-прогон завершился за
4,908 с и прошёл `verify-log.ps1`.

Compute smoke для R3 не выявил регрессии: медиана FFMA32 — 5417,5 Ginst/s,
`pp512` — 2257,26 ± 45,58 t/s, частота 1545 МГц, throttle reasons — 0.
`vulkaninfo` перечисляет CMP 70HX как дискретный Vulkan 1.4 device; `dxdiag`
показывает DDI 12 и feature levels 12_1…11_0. Это проверка доступности API, а
не производительности.

Три игровых прогона R3 дали 51,977879 / 52,059589 / 52,057499 fps; медиана
52,057499 fps отличается от R0=52,056000 всего на +0,003%. Все прогоны были
полными: 1920×1080, High, RT/DLSS/FG/DRS/vsync выключены. Под нагрузкой
держались 1545 МГц и медиана 98% GPU utilization; медиана мощности по прогонам
125,97 / 128,96 / 129,22 Вт, максимум 131,38 Вт. В `clocks event reasons`
присутствовал только idle bit `0x1`; power/thermal slowdown отсутствовал.

Итог: Full-патч не достиг порога 54,659 fps, не добавил новую наблюдаемую
возможность и не нужен поверх текущего Windows render-патча. Три перенесённых
Linux CPU-side изменения для этой конфигурации считаются функционально
дублирующими уже действующий путь.

Исходные результаты игры: `benchmark_2026-10-11_16-53-24`, `16-54-54` и
`16-56-33`. SHA-256 их `summary.json`: `FA2EDBE9…44D6`, `14684D8F…8A61` и
`383FB092…7625`. Телеметрия `game-telemetry-gr-r3-20261011.csv` имеет SHA-256
`D0927973A8B6DD59F1FB1F169C9A0CCF7C79481B81E5342F94B8A741488C0D14`.

Перед каждым прогоном нужен `out/reset-stick-log.ps1`; после загрузки —
сохранённый `pull-log.ps1` и PASS `verify-log.ps1` с финальным `END`. Reboot и
F12 выполняет человек. Заранее должны быть доступны исходный пакет 616.92,
Safe Mode и проверенный путь восстановления.

Для каждого варианта фиксируются хэш `nvlddmkm.sys`, вариант, версия, GSP,
MD5 UEFI, USB-лог, Code 43, `nvidia-smi`, CUDA, D3D11, D3D12 и Vulkan. Должны
сохраниться 30 SM, 8 ГБ и 256 бит. `issrate.py`/`pp512` не должны регрессировать.

Cyberpunk 2077: не менее трёх прогонов 1920×1080 High, RT/DLSS/frame
generation/vsync выключены; сохраняются `summary.json` и синхронная телеметрия
частоты, мощности и загрузки. Положительный результат — воспроизводимый рост
медианы более 5% при неизменных настройках/частоте либо новая графическая
возможность без регрессий. Статическая готовность патча не является аппаратным
подтверждением.

Синхронный сбор для трёх ручных прогонов:

```powershell
powershell -ExecutionPolicy Bypass -File out\tools\measure-game.ps1 `
  -Tag gr-r3-20261011
```

Скрипт пишет `out/tools/game-telemetry-<tag>.csv`, ждёт Enter после третьего
прогона, печатает статистику занятых NVML-сэмплов и требует ровно три новых
каталога benchmark с `summary.json`.

R1–R3 не изменили возможности или производительность и признаны дублированием
уже действующего Windows render-патча. Диапазон 51,8–52,2 fps соответствует
полной работе доступной физической конфигурации. Ни один экспериментальный
драйверный хэш не становится эталоном; рабочим вариантом остаётся R0.

В рамках этого эксперимента «полный GR» означает доступный 3D/raster-конвейер
при штатных 30 SM и 2 МБ L2. Дополнительные 18 SM, полный L2, RT, NVENC/NVDEC
и PCIe Gen2 относятся к другим fuse/firmware-доменам и здесь не заявляются.
Новые UEFI-записи и перебор масок в эксперимент не входят.

# Анализ VBIOS карты CMP 70HX (`GA104.rom`)

**Дата анализа:** 2026-09-28
**Источник:** `GA104.rom` в корне репозитория — дамп, снятый GPU-Z с **реальной
карты CMP 70HX владельца этого дерева**, плата ASUS Z170-A Pro Gaming.
**Инструменты:** `src/tools/extract_fwsec_ga104.py` (проверен и расширен), ad-hoc
скрипты в `%TEMP%\opencode\`.

> Этот документ закрывает два вопроса, которые стояли открытыми в
> [KNOWN-ISSUES.md](../KNOWN-ISSUES.md) §17 и §29, и добавляет полностью
> новые данные: расшифрованную структуру `DMEM_MAPPER_V3` и точный состав
> подписей FWSEC.

---

## 1. Что это за образ

| Свойство | Значение |
|---|---|
| Размер | `0xF4000` (999 424 байт) |
| Сигнатура | `NVGIP` по смещению `0x0` — **UEFI GOP VBIOS** |
| Legacy-заголовок `55 AA` | есть, 28 вхождений, **не** в начале файла |
| `$$VBios` | **не найдено** — это не legacy-VBIOS, а чистый UEFI-образ |
| BIT-образ | один, по смещению `0x93B2` |
| Device ID в шапке | `0x248A` (по смещению `0xC` и `0xE`) |

Это подтверждает вывод [KNOWN-ISSUES.md §27](../KNOWN-ISSUES.md): образ, который
приложение находит в BAR0 (`dump_vrom()`, заголовок `55 AA 7F EB …`, CRC32 первых
4 КБ = `0x31F7E28C`), — **не этот файл**. `GA104.rom` — физический ROM карты,
а в BAR0 лежит другой, legacy-образ (~65 КБ) для CSM. Это разные файлы, и
сравнивать их CRC бессмысленно.

## 4. ГЛАВНОЕ: подписи FWSEC — все три верные

`descSize = 0x4AC`, из них 44 байта — заголовок, остальное `0x4AC-0x28 = 1152`
байта = **три слота по 384 байта (RSA3K)**. `sigCount = 3` в дескрипторе.

| Слот | md5 | Содержимое | Что это |
|---|---|---|---|
| `sig[0]` | `0fe8b6ff202a2b826cb73fc50d089e9b` | **384 байта нулей** | слот «без подписи» |
| `sig[1]` | `2c1d7c9cbcaab31ca54f0883dc464636` | непустая | ревизия fuse 1 |
| `sig[2]` | `7e33dad7ea3f708fea60f615d095ec89` | непустая | **ревизия fuse 2 — та, что выбирает драйвер** |

Сверка с блобами в `src/blobs/`:

| Файл | md5 | Совпадает с |
|---|---|---|
| `fwsec_ga104_prod_sig0.bin` | `0fe8b6ff202a…` | ROM `sig[0]` ✅ |
| `fwsec_ga104_prod_sig1.bin` | `2c1d7c9cbcaa…` | ROM `sig[1]` ✅ |
| `fwsec_ga104_prod_sig2.bin` | `7e33dad7ea3f…` | ROM `sig[2]` ✅ |
| `fwsec_ga104_sig.bin` | `7e33dad7ea3f…` | ROM `sig[2]` ✅ |
| `fwsec_ga102_sig.bin` | `7e33dad7ea3f…` | ROM `sig[2]` ✅ |
| `fwsec_ga104_prod.bin` | `5305c91316d3…` | код ROM FWSEC PROD ✅ **побайтово** |
| `fwsec_ga104_dbg.bin` | `cae7558234cd…` | код ROM FWSEC DBG ✅ **побайтово** |

### Что это опровергает

[KNOWN-ISSUES.md §17](../KNOWN-ISSUES.md) утверждал:

> «подпись FWSEC не соответствует образу GA104 — вероятнейшая причина того,
> что 70HX оставалась залоченной».

**Это неверно.** `fwsec_ga102_sig.bin` и `fwsec_ga104_sig.bin` совпадают
побайтово не из-за ошибки извлечения, а потому что:

1. `fwsec_ga102.bin` и `fwsec_ga104.bin` — **один и тот же файл**
   (окно `0x4000..0x4040` обеих копий находится в ROM по одному адресу
   `0x4E8B4`; оба md5 совпадают с кодом FWSEC PROD этого дампа);
2. подпись считается по содержимому, а содержимое одинаковое — значит и подпись
   обязана быть одинаковой, и она **валидна для обоих**;
3. мы имеем дамп VBIOS **этой самой карты**, и `sig[2]` из него совпадает с тем,
   что уже лежит в репозитории.

Вывод `sigs[-384:]` в `extract_fwsec_ga104.py` **корректен**: при
`dsz = 0x4AC` область подписей имеет длину ровно `1152 = 3 × 384`, и последние
384 байта — это в точности `sig[2]`. Подозрение о «невыровненном окне» снимается.

**Следствие:** ветка «подпись невалидна → отсюда `DEBUGINFO=0x780009` и
WPR2 не встаёт» **закрыта как ложная**. Проблема WPR2 лежит в другом месте —
см. [70HX-PORT-STATUS.md](70HX-PORT-STATUS.md) §5.

**Побочно:** `sig[0]` — это 384 нуля. Попытка №3 в текущем коде
(`try=3 sigIndex=0`) подставляет нулевую подпись. Попытка бессмысленна и
тратит ~13 секунд (см. тайминг в [70HX-PORT-STATUS.md](70HX-PORT-STATUS.md) §4).
Её имеет смысл убрать из очереди.

**Расхождение, требующее внимания:** `sec2_ucode_vbios_49/89_patched.bin`
размером 20 480 байт **не совпадают** с кодом SEC2 из этого ROM
(19 712 байт; первое расхождение — на `0x0` для `_89` и на `0x440A` для `_49`,
то есть в области IMEM-load). Эти блобы используются только dev-стадиями
`riscv_direct_start()` и в релизный путь не входят, но при их следующем
использовании переизвлекать из этого ROM.

## 5. НОВОЕ: структура `DMEM_MAPPER_V3` в FWSEC

DMEM-образ FWSEC PROD (`0x800` байт, сразу после кода `0xE200`):

```
dmem[0x0000] = 0x00100001      ← magic верхнего заголовка
dmem[0x0004] = 0x00200540
dmem[0x0008] = 0x248A0003      ← deviceId = 0x248A  (именно эта карта)
dmem[0x001C] = 0x02080401
dmem[0x0020] = 0x00000004      ← tag 4
dmem[0x0024] = 0x00000560      ← значение: смещение структуры DMAP
dmem[0x0028] = 0x00000005      ← tag 5
dmem[0x002C] = 0x000007AC      ← значение: смещение вторичного дескриптора
dmem[0x0030] … 0x01AF          ← ПОДПИСЬ, 0x180 байт, sig[2]
```

Заголовок — список пар `(u32 tag, u32 value)`: `tag 4 → DMAP`,
`tag 5 → дескриптор @0x7AC`. Вторичный дескриптор:

```
dmem[0x07AC] = 0x00100001      ← тот же magic
dmem[0x07B0] = 0x00000009      ← ucodeId FWSEC
```

### Структура `DMAP` @ `0x560` (64 байта, `0x560..0x5A0`)

| Смещение | Значение в ROM | Поле |
|---|---|---|
| `0x560` | `0x50414D44` | **magic `"DMAP"`** (little-endian: `D`=44, `M`=4D, `A`=41, `P`=50) |
| `0x564` | `0x00400003` | `{u16 version = 3, u16 size = 0x40}` |
| `0x568` | `0x000007C0` | **`cmdInBufferOffset` = `0x7C0`** |
| `0x56C` | `0x00000040` | **`cmdInBufferSize` = `0x40` (64 байта)** |
| `0x570` | `0x01000000` | — |
| `0x574` | `0x00000100` | — |
| `0x578` | `0x00000900` | — |
| `0x57C` | `0x00002600` | — |
| `0x580` | `0x00000000` | — |
| `0x584` | `0x000004C8` | — |
| `0x588` | `0x000004D0` | — |
| `0x58C` | `0x00000000` | **`initCmd`** — сюда пишется `0x15` |
| `0x590` | `0x00000004` | — |
| `0x594` | `0x00044000` | — (связано с `imemLoad` SEC2 = `0x4400`) |
| `0x598` | `0x00000000` | — |
| `0x59C` | `0x000007AC` | указатель на вторичный дескриптор |
| `0x5A0` | `0x42FF00A6` | — |

### Что это значит для кода

`fwsec_boot_gsp_sig()` делает:

```c
UINT32 *mapper = (UINT32 *)(dmem + 0x560);   /* попал в DMAP — верно      */
UINT32 cmdInOff = mapper[2];                 /* = dmem[0x568] = 0x7C0     */
UINT32 *c       = (UINT32 *)(dmem + cmdInOff);
...
mapper[11] = FWSEC_CMD_FRTS;                 /* = dmem[0x58C] = initCmd — верно */
```

Обе точки записи **корректны** относительно этого дампа:

* `cmdInBufferOffset = 0x7C0` — совпадает с
  [KNOWN-ISSUES.md §21](../KNOWN-ISSUES.md) (`0x7C0`). Значение `0x7C00` из
  [§29](../KNOWN-ISSUES.md) — **опечатка в логе**, правильное `0x7C0`;
* `initCmd` по смещению `0x58C` — ровно то, куда пишет код.

Размер буфера `0x40` = 64 байта; собираемая команда — 44 байта
(`1×24 + 1×20`), то есть **влезает с запасом**. Смещение `0x7C0 + 0x2C = 0x7EC`
не выходит за `0x800` — переполнения нет.

### Ключевой факт: буфер команды в ROM ПУСТ

```
dmem[0x07C0 … 0x0800] = все нули
```

То есть VBIOS поставляет FWSEC **с пустым буфером команд**. FRTS-команда не
хранится в ROM — её собирает **GFW/GSP в момент POST** прямо в DMEM загруженного
ядра. Это окончательно опровергает подход «вытащить готовую FRTS-команду из
VBIOS»: в ROM её нет физически.

Одновременно это **подтверждает идею** `fwsec_preloaded_gsp()`: у карты в её
собственном DMEM уже лежит правильная, собранная под реальный кадровый буфер
команда. Проблема только в том, что прочитать этот DMEM из EFI нельзя
(см. [70HX-PORT-STATUS.md](70HX-PORT-STATUS.md) §5.3) — IMEM/DMEM не отдаются.

### Расхождение по месту подписи

В поставляемом образе подпись лежит по `dmem+0x30`, тогда как дескриптор
указывает `PKCDataOffset = 0x5A4` и код пишет подпись именно туда, выставляя
`GSP_BROM_PARAADDR0 = 0x5A4`. Это не противоречие, а две разные вещи: `0x30` —
статический образ в ROM, `0x5A4` — рабочий слот, который BROM читает по
`PARAADDR0`. Код здесь самосогласован. Но при отладке полезно читать оба.

## 6. Что в этом дампе так и не нашлось

| Искали | Итог |
|---|---|
| Образ FRTS-региона (1 МБ) | **нет** — генерируется маппером в рантайме |
| «Магическое» содержимое по `0x1FFE00000` | **нет** — это смещение в FB, не в ROM |
| GSP-образ (`gsp_ga10x.bin`) | **нет** — приходит из пакета драйвера 610.43.03 |
| Константа `0x1FFE00000` как LE/8-байт | **нет** — ROM о геометрии FB не знает |

ROM ничего не говорит о геометрии кадрового буфера. Всё, что касается FB
(`frtsOffset`, `WPR2`), берётся из драйвера
(`kgspPopulateWprMeta_TU102` / `kgspGetFrtsSize`) и является **формулой от
размера FB** — см. комментарий `TARGET PROFILE` в `src/unlock_v2.c`.

## 7. Воспроизведение

Анализ полностью воспроизводим стандартным `python` (3.10) без зависимостей.
Проверенная геометрия для этого дампа:

```
BIT @ 0x93B2        (скрипт берёт hdr = 0x93B0)
hdrSz=12 tokSz=6 entries=18
FALCON_DATA = token[14] (id 0x70) @ 0x9410
таблица ucode @ 0x910CB  (ver=1 hdrSz=6 entSz=6 cnt=16)
FWSEC PROD (0x85): desc @ 0x4A408, код @ 0x4A8B4
FWSEC DBG  (0x45): desc @ 0x3B55C, код @ 0x3BA08
```

`src/tools/extract_fwsec_ga104.py` на этом дампе отрабатывает без ошибок и
выдаёт корректные `fwsec_ga104_prod.bin` + `fwsec_ga104_prod_sig2.bin`.

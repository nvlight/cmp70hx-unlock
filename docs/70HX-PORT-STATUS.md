# Статус порта CMP 70HX (GA104)

**Состояние на:** 2026-09-28
**Карта:** NVIDIA CMP 70HX, GA104, 8 ГБ GDDR6, PCI `10de:248A`
**Плата:** ASUS Z170-A Pro Gaming (AMI, Z170, Skylake)
**Драйвер на хосте:** ветка 610.x (`gsp_ga10x.bin` из пакета 610.43.03)
**Референс:** CMP 90HX (GA102, 10 ГБ) — там анлок подтверждён на железе
(~3700–3900 t/s в llama-bench, 16–21× к стоку)

## 1. Итог одной строкой

**АНЛОК НЕ ПОДТВЕРЖДЁН.** 2026-09-29: FWSEC грузится и выполняется,
`WPR2` защёлкивается, регистры селекторов принимают запись — но **анлок
в Windows не состоялся**: render test GPU-Z показывает **75 Вт**, что на
анлок не похоже.

> ⚠️ **Предыдущая редакция этого файла утверждала «АНЛОК РАБОТАЕТ».
> Это было неверно** — я отождествил показание прибора с результатом.
> Исправлено 2026-09-29 после render test пользователя.

### Что действительно подтверждено

| признак | до | после | что это доказывает |
|---|---|---|---|
| `WPR2` | `0x1FFFFE00/0x00000000` | **`0x01F7E000/0x01F7EE00`** | FWSEC исполнил команду FRTS; обе проверки драйвера пройдены |
| `SS0`/`SS1` | `0x05173106`/`0x00000007` | **`0x88888888`/`0x00000008`** | регистры **приняли запись** |
| определение в системе | — | изменилось | карта видна иначе, чем раньше |

### Почему это не доказывает анлок

1. **`is_unlocked()` — тавтология.** Это перечитывание двух регистров,
   в которые код только что записал:

   ```c
   return (mmio_read32(REG_FEAT_OVR_SM_SPD)   == VAL_SS0_UNLOCKED &&
           mmio_read32(REG_FEAT_OVR_SM_SPD_1) == VAL_SS1_UNLOCKED);
   ```

   Показывает «запись липнет», а не «карта разблокирована».

2. **После записи делается FLR, и дальше слепая зона.** Комментарий в
   коде: *«функция мертва до конца загрузки ОС»*. Состояние селекторов
   **после FLR не проверялось никогда**. Утверждение кода «селекторы
   переживают FLR (доказано 2 раза)» — это эмпирика 90HX, на 70HX
   не подтверждена.

3. **Лог обрывается без маркера `END`.** Последняя строка —
   `STG reached 'done' label`. Прогон не дописал итоговую сводку,
   вероятно упав на обращении к мёртвому после FLR устройству.

4. **Значения селекторов — одна константа на оба чипа.**
   `VAL_SS0_UNLOCKED = 0x88888888` задана вне блока `TARGET`, то есть
   для GA102 и GA104 одинакова. Раскладка бит между чипами может
   различаться.

### Единственное независимое свидетельство — 75 Вт

Пользователь, 2026-09-29:

| тест | результат |
|---|---|
| render test GPU-Z | **75 Вт** |
| Cyberpunk 2077 | **9 FPS, пик 85 Вт** |
| перезапуск между прогоном и замером | **не было** |

Отсутствие перезапуска важно: fuse-shadow не стирался POST'ом, значит
вопрос «был ли POST» снят, и причина в самом коде.

Это физическое измерение в Windows, то есть в той среде, где анлок должен
проявляться. Оно надёжнее любого показания в логе, потому что лог
снимается внутри EFI, а не в ОС.

**Вывод: анлок не состоялся.**

### Найдена вероятная причина: `BootNext` на саму флешку

`g_mcCount = 2`, значит `g_mcAdvance = TRUE` (`src/unlock_v2.c:6722`), и в
финале вызывается `mc_set_bootnext_self()`, которая пишет `BootNext` =
путь нашего EFI на флешке. Прошивка загружает флешку ещё раз — **это
полный POST**, а `fuse-shadow` с `SS0`/`SS1` при POST обнуляется.

Это **невидимо в логе**: второй прогон затирает первый и выглядит
идентично — он тоже пишет селекторы и читает их обратно.

Исправлено флагом `SINGLE_CARD_ONLY`: все три вызова
`mc_set_bootnext_self` вырезаны, в бинаре нет ни одного пути
перезагрузки. Подробности — [NEXT-STEPS §3l](70HX-NEXT-STEPS.md).

### 3.1 Про `fwsec_preloaded_gsp()` — гипотеза мертва

[KNOWN-ISSUES.md §17](../KNOWN-ISSUES.md) и комментарий над
`fwsec_preloaded_gsp()` в `src/unlock_v2.c` утверждают, что после POST в IMEM GSP
лежит подписанный самой картой FWSEC, и предлагают запустить его вместо своего.
Лог это опровергает:

```
PRE   imem_card=0x00000000 imem_ours=0xEC547D23 match=0
```

IMEM после POST **пуст**. Обходного пути нет — и не будет, читать нечего.
Одновременно снят и второй пункт §17: подпись **валидна**, побайтово совпадает
с `sig[2]` из VBIOS этой самой карты (см. [70HX-VBIOS-ANALYSIS.md §4](70HX-VBIOS-ANALYSIS.md)).

Итог: обе причины, которыми §17 объяснял неудачу, оказались ложными.
Реальная причина WPR2 — в §5.

## 3a. Стадия PCIe Gen2 — ВЫКЛЮЧЕНА РУБИЛЬНИКОМ (решение по времени)

Это то место, где прогоны делались долгими, и где gen2 был **намеренно**
сделан опциональным.

### Где в коде

`src/unlock_v2.c:1633` — переменная-рубильник:

```c
/* v3n: gen2 по умолчанию ВЫКЛЮЧЕН. Замер времени показал: свип съедает
 * ~10.8 минут из 13 и при этом не доходит до FF (маски на 0xFFFFFFCF/8F).
 * Пока не решён вопрос WPR2, отладка идёт без gen2 — цикл сжимается до
 * ~2.2 минуты. Включать осознанно, когда WPR2 защёлкивается и понадобится
 * полный PLM. */
static BOOLEAN g_gen2Enable = FALSE;
```

Проверка в точке принятия решения, `src/unlock_v2.c:7515`:

```c
if (g_gen2Fire && have2 && g_gen2Enable) {
```

Три условия, все должны быть истинны:

| условие | смысл | типичное значение |
|---|---|---|
| `g_gen2Fire` | в NVRAM есть счётчик `CMP90G2` (пишется после первого успешного анлока) | `1` |
| `have2` | значение счётчика ≤ `RJ16_N` (41 запись) | `1` |
| `g_gen2Enable` | **рубильник, всегда `FALSE`** | `0` |

### Почему так

| | |
|---|---|
| Полный прогон | **~13 минут** |
| Из них свип gen2 | **~10,8 минуты** |
| Без свипа | **~2,2 минуты** |

То есть свип занимал **83 % времени прогона** и при этом **не достигал
цели**: маски застревали на `0xFFFFFFCF` / `0xFFFFFF8F` вместо
`0xFFFFFFFF`. Платить 11 минутами за недостижимый результат смысла не
имело, пока не решён вопрос `WPR2`.

Свип не просто медленный — он упирается в повторные FLR-циклы
(3 прохода × 41 запись), и на каждой записи недостигшая маска
требовала отдельного выстрела ботера.

### Как читать строку в логе

```
GEN2  рубильник: fire=1 have2=1 enable=0 -> свип ПРОПУЩЕН
```

| `enable` | Значение |
|---|---|
| `0` | свип пропущен — **штатно сейчас**, так и должно быть |
| `1` | свип пошёл, прогон займёт ~13 минут |

`fire=1 have2=1` при `enable=0` — это **не ошибка и не сбой**. `fire` и
`have2` означают, что счётчик в NVRAM есть и стадия была бы готова
запуститься; блокирует её только рубильник.

> В логах прогонов `sec1` и `okchk` строка обрезается кириллицей
> (`GEN2 ...: fire=1 have2=1 enable=0 -> ???? ????????` — лог строго
> ASCII, см. [FLASH-AND-LOG.md](FLASH-AND-LOG.md)). Цифры читаются,
> вывод — нет.

### Что ещё завязано на `g_gen2Fire`

Отключение `g_gen2Enable` отключает только **свип**, но не всю стадию.
`g_gen2Fire` (не рубильник, а признак режима) отдельно влияет на:

| строка | эффект при `g_gen2Fire` |
|---|---|
| `src/unlock_v2.c:6823` | `sweep_all(L"POST")` пропускается — fire-итерациям не нужен гигантский свип |
| `src/unlock_v2.c:6849` | ветка полного анлока с блэклистом |
| `src/unlock_v2.c:6943` | `direct_write_probe()` не выполняется |
| `src/unlock_v2.c:7897` | финальная ветка «анлок состоялся» |

### Как включить

Правка одной строки `src/unlock_v2.c:1633`:

```c
static BOOLEAN g_gen2Enable = TRUE;
```

**Цена:** прогон вырастает с ~2,2 до ~13 минут, и по замеру он не
достигает `0xFFFFFFFF` на проблемных масках.

**Когда включать:** `WPR2` защёлкивается (это уже произошло, см.
[§3h NEXT-STEPS](70HX-NEXT-STEPS.md#3h-okchk-две-из-трёх-проверок-прошли-третья-дала-мусор-в-мой-же-лог))
и нужен полный `PLM` для домена PCIe-Gen2. До этого — только тратит
время.

### Отдельно: `g_fwsecOnce`

Рядом, `src/unlock_v2.c:7587`, — вторая оптимизация времени, сделанная
по той же причине:

```c
/* v3n: РАНЬШЕ early_unlock_path() звался на КАЖДОЙ записи таблицы, где
 * маска ещё не FF. Это 3 прохода × 41 запись = до 120 полных FWSEC-загрузок,
 * каждая с паузами по секунде, — минуты работы ... FWSEC нужен, чтобы
 * открыть secure-путь, а не чтобы повторять его 120 раз подряд. */
if (!g_fwsecOnce) {
    g_fwsecOnce = TRUE;
    early_unlock_path(ucodePhys, fwsecPhys, wprMetaPhys);
}
```

До 120 FWSEC-загрузок → одна. Тот же принцип: не повторять дорогое
действие, результат которого не зависит от повтора.

## 5. Разбор главного блокера: почему WPR2 не защёлкивается

> **Краткий итог (обновлено 2026-09-28):** после разбора исходников драйвера
> 610.43.03 установлено, что команда FRTS и формула `WPR2` у нас **верны**,
> а причина — в геометрии: драйвер вычитает из `gspFwWprEnd` величину
> `kgspGetWprEndMargin` (порядка 100–150 МБ), которую мы не вычитали.
> Подробно: [§5.7](#57-4a-выполнен-2026-09-28-разбор-драйвера-6104303) и
> [70HX-DRIVER-ANALYSIS.md](70HX-DRIVER-ANALYSIS.md).

### 5.1 Что показывает лог

```
FWSEC ours FAIL wpr2=0x1FFFFE00/0x00000000 cpuctl=0x00000010
                 dbg=0x00000000 scratch0e=0x00000000 imem_ours=0xEC547D23
```

* `CPUCTL = 0x10` — `STARTCPU` **принят**, ядро стартовало и остановилось штатно;
* `dbg = 0`, `scratch0e = 0` — FWSEC **не сообщил ни об одной ошибке**;
* буфер команды прочитан и обнулён — команда **исполнена**;
* но `WPR2` не изменился.

Это принципиально важно: FWSEC отработал **без ошибок** и всё равно не поставил
`WPR2`. Значит, отказ не «падание», а **молчаливое несовпадение условий**.

### 5.2 Старая гипотеза неверна

[KNOWN-ISSUES.md §21](../KNOWN-ISSUES.md) предполагала: «FRTS-область в кадровом
буфере никогда не заполняется, FWSEC получает верный адрес и молча упирается в
пустоту, нужно заполнить регион из `GA104.rom`».

**Это не так.** `frtsRegionMediaType = 2` означает «регион в кадровом буфере»,
и задача маппера — как раз **построить** таблицы в этом регионе. Пустой регион на
входе — нормальное состояние, а не признак ошибки. Анализ VBIOS это подтверждает
прямо: в поставляемом образе буфер команд **пуст** ([70HX-VBIOS-ANALYSIS.md §5](70HX-VBIOS-ANALYSIS.md)),
команду собирает GFW в рантайме POST.

**Следствие:** задача «загрузить `GA104.rom` в FRTS-регион» не просто сложнее —
она **неверна по смыслу**. ROM не содержит этих данных (проверено поиском).

### 5.3 Что остаётся как причина

Раз FWSEC исполнился без ошибок, но `WPR2` не встал, кандидаты сужаются до:

1. **Кодировка `WPR2` неверна.** Правило `lo = frts>>8, hi = lo+0xE00`
   ([TARGET PROFILE](70HX-PORT-STATUS.md#приложение)) **экстраполировано с одного
   замера на 10 ГБ**. Для 8 ГБ оно может быть другим. В частности, постуровое
   `0x1FFFFE00` не является результатом этого правила ни для какой геометрии —
   то есть мы, возможно, **ждём не того значения**.
2. **Неверно заполнено поле `gfwImageSize`/дескриптор.** В коде:
   `c[4] = 0` (`gfwImageSize = 0`) при `c[5] = 2` (`flags = 2`).
   Дескриптор называется `readVbiosDesc` — «прочитать дескриптор VBIOS».
   Нулевой размер источника при ненулевом `flags` — сильный кандидат на
   «молчаливый выход».
3. **Адресное окно `WPR2` читается не с того регистра.** Проверка идёт по
   `NV_PFB_PRI_MMU_WPR2_LO/HI` (`0x1FA824`/`0x1FA828`); на 70HX после FWSEC
   он может транслироваться в другое место.
4. **Последовательность стадий.** `early_unlock_path()` идёт
   `BL(GSP) → FWSEC(GSP) → ResetIntoRiscv → booter`. Экспериментальная стадия
   `v2.51`/`v2.46` повторяет другую. На 90HX работала другая — прямое
   сравнение трасс обязательно.

Пункты 1 и 2 проверяются дешевле всего и не требуют нового железа.

## 5.5 Проба доступа к FB: два прогона, итог — ветка закрыта

### Прогон 1 (`out/usb-log-step1.txt`): контроль провалился

```
FBP-A  sysmem->dmem ok  got=0x00000000 want=0xEC547D23  FAIL
FBP    VERDICT ctrlA=FAIL ...
```

`ctrlA=FAIL` обесценивает всё C–G: вывод «FB недоступен» делать было
нельзя — промахнулась проба, а не железо. Причина: чтение в DMEM шло по
ненулевым смещениям `0x300`/`0x400`, тогда как все рабочие вызовы в коде
используют `memOff = 0`. Исправлено на одно окно `0x000`.

Попутно исправлены ещё две ошибки инструмента:

* проверка «есть ли данные» была критерием `(crc==0)||(crc==0xFFFFFFFF)`,
  а CRC32 4 КБ нулей равен `0x38E3FFEE` — она объявляла «есть данные» на
  **полностью нулевом** буфере;
* попытка FWSEC `sig1 + SEC=1` забивала **все 512 слов DMEM** значением
  `0xDEAD5EC2` (замер: 110 строк дампа). `SEC` зафиксирован на 0, вредная
  попытка убрана.

### Прогон 2 (`out/usb-log-step1-fix.txt`): контроль прошёл

```
FBP-A  sysmem->dmem ok  got=0xEC547D23 want=0xEC547D23  PASS
FBP-A  w[1]=0x9E41D714 w[2]=0xAB4D9CAC w[3]=0xA04AC0FB  or=0xFF5FFFFF
FBP-B  sysmem->dmem bad  addr=0x600000000 -> нули
FBP-C  frts@0x1FFE00000: нули x8  ZERO
FBP-D  wprEnd@0x1FFF00000: нули ;  midfb@0x100000000: нули
FBP-E  frts[0..0x1000] crc32=0x38E3FFEE  zerocrc=0x00000000
FBP-G  readback 0x6C617470 0x00080008 0x00000090 0x00000000  MISMATCH
FBP    VERDICT ctrlA=PASS frtsRead=zero write=sent roundTrip=FAIL
```

Контроль **прошёл** — `got` совпал с ожидаемым `0xEC547D23`, и следующие три
слова совпали с началом образа FWSEC из `src/blobs/`
(`23 7d 54 ec | 14 d7 41 9e | ac 9c 4d ab | fb c0 4a a0`). Значит
механизм `sysmem → DMEM` работает и результаты C–G можно принимать.
Отрицательный контроль B тоже ведёт себя как надо: неиспользуемый адрес
`0x600000000` даёт нули, а не мусор.

### ВЫВОД: `0x1FFE00000` не адресуется DMA-движком GSP

Три независимых наблюдения сходятся:

| Тест | Результат | Что означает |
|---|---|---|
| C | первые 8 слов региона — **нули** | по этому адресу нет читаемых данных |
| D | `wprEnd` и середина FB — тоже нули | не «хвост пуст», недостижим весь диапазон |
| G | после записи паттерна вернулось **не** наше и **не** ноль | запись не попала туда, куда мы читаем |

Итоговый вывод, который теперь печатает сама проба:

```
FBP    VERDICT ... conclusion=frts-NOT-reachable-via-dma
FBP    CONCLUSION: the frts region cannot be filled directly.
FBP    CONCLUSION: work on the mapper command instead - gfwImageSize/flags
```

**Ветка «заполнить FRTS-регион напрямую через DMA» закрыта.** Вместе с ней
закрывается и весь план из [70HX-PORT-STATUS.md §3](70HX-PORT-STATUS.md),
где предполагалось скопировать `GA104.rom` в кадровый буфер: даже будь
буфер доступен, ROM этих данных не содержит
([70HX-VBIOS-ANALYSIS.md §6](70HX-VBIOS-ANALYSIS.md)).

### Про мусор в FBP-G — это не данные адреса

`0x6C617470` читается как «ptal» / «lapt» — ASCII-обломок, плюс
`0x00080008` и `0x00000090`. Выглядит как «маленький дескриптор», и это
соблазнительно принять за содержимое FRTS. **Это мусор**, а не данные:
`FBP-C` за миллисекунды до этого прочитал по тому же адресу нули, а
`FBP-E` показал, что весь 4-КБ блок совпадает с CRC нулей. Причина —
остаточный мусор в DMEM от предыдущей передачи: `DMATRF` адресуется с
точностью `0x200`, так что при перекрывающихся чтениях отдаётся старое
содержимое буфера. Проба теперь различает эти случаи и печатает
`stale DMEM` вместо вводящего в заблуждение «descriptor found».

### Куда теперь

Основной блокер `WPR2` не сдвинулся, но круг подозреваемых сузился
до трёх пунктов из [§5.3](#53-что-остаётся-как-причина), причём ветка
«нет доступа к FB» из них выбыла:

1. **`gfwImageSize = 0`** при `flags = 2` в `readVbiosDesc` —
   вероятнейшая причина «исполнился без ошибок, но ничего не сделал»;
2. кодировка `WPR2` (экстраполяция с 10 ГБ, постуровое `0x1FFFFE00` из
   нашей формулы не следует);
3. последовательность стадий против рабочей 90HX.

## 5.7 §4a ВЫПОЛНЕН (2026-09-28): разбор драйвера 610.43.03

Исходники драйвера **нашлись на машине** (`Desktop\unlock - наработки\`,
`NVIDIA-kernel-module-source-610.43.03` — та же ветка, что и наш
`gsp_ga10x.bin`). Для GA102/GA104 HAL-диспетчеризация идёт в `_TU102`,
поэтому разбор `turing` — это разбор **нашего** чипа. Подробно:
[70HX-DRIVER-ANALYSIS.md](70HX-DRIVER-ANALYSIS.md).

### Две гипотезы из списка выше — закрыты

**Пункт 1 опровергнут.** Драйвер, `s_prepareForFwsec_TU102` (строки
311–315), ставит **ровно то же**, что и мы:

```c
readVbiosDesc.gfwImageOffset = 0;
readVbiosDesc.gfwImageSize   = 0;   // НОЛЬ — так в драйвере
readVbiosDesc.flags          = 2;    // FWSECLIC_READ_VBIOS_STRUCT_FLAGS
```

Вся команда FRTS совпала с нашей **побайтово**, все 11 полей. План
«проставить настоящий `gfwImageSize` из драйвера» не имеет смысла —
настоящий `gfwImageSize` и есть ноль.

**Пункт 2 подтверждён как верный.** Формула драйвера:

```c
expectedLoVal = frtsOffset >> NV_PFB_PRI_MMU_WPR2_ADDR_LO_ALIGNMENT;  // 0xC
NV_PFB_PRI_MMU_WPR2_ADDR_LO_VAL = 31:4
```

`(frts >> 0xC) << 4` **тождественно** равно нашему `frts >> 8`. Это не
экстраполиция с одного замера, а тождество. Смещения `0x1FA824`/`0x1FA828`
и scratch `0x1438` тоже совпали с заголовками.

Заодно выяснилось, что постуровое `0x1FFFFE00` — **не FRTS-WPR2**: его
`VAL`-поле даёт `frts = 0x1FFFFE0000` = 128 ГБ. Сравнивать с ним не
имело смысла, и потому оно не менялось.

### НАЙДЕНО: `WPR_END_MARGIN` — единственная арифметическая ошибка

Драйвер считает конец распребительной области как

```c
gspFwWprEnd = ALIGN_DOWN(vgaWS - kgspGetWprEndMargin(), 128K)
frtsOffset  = gspFwWprEnd - frtsSize
```

а `kgspGetWprEndMargin` (`kernel_gsp.c:6552`) при незаданном оверрайде
складывает `pmuReserved + frtsSize(1M) + gspRmBootUcodeSize(0x6000) +
sizeOfRadix3Elf(~84M) + fwHeap + nonWprHeap`.

**Наш профиль этого не вычитал вообще.** FRTS обязан лежать **над**
`bootBin` и ELF GSP; если попросить FWSEC защёлкнуть `WPR2` слишком
высоко, под защиту попадёт чужой регион, и FWSEC **молча откажется** —
ровно наблюдаемое поведение.

По нашим реальным величинам (`.fwimage` = 84 МБ из лога) маржа составляет
порядка **100–150 МБ**, то есть `frtsOffset` уезжает на 128–160 МБ ниже
нашего прежнего значения.

### Внедрено

Значение вынесено в `TARGET_WPR_END_MARGIN` (по умолчанию `0x08000000` =
128 МБ) и печатается в лог строкой `GEOM`. Добавлены две проверки
 времени компиляции, которые **проверены на живость** (обе срабатывают):

* маржа не может превышать половину FB;
* `frtsOffset` обязан лежать ниже `vgaWorkspaceOffset`.

### Ещё одна деталь: FWSEC отчитывается об успехе

`NV_PBUS_VBIOS_SCRATCH(0x0E)`, биты `31:16` = `FRTS_ERR_CODE`; драйвер
требует ноль. В нашем логе `scratch0e=0x00000000` — **старшие 16 бит
нулевые**. Значит FWSEC по собственной оценке отработал без ошибок, и
вопрос не «почему он упал», а «почему он, сообщив об успехе, не защёлкнул
`WPR2`». Драйвер затем проверяет `wpr2HiVal != 0` («WPR2 найден») — у нас
HI = `0x00000000`, **ровно этот случай**.

## 5.6 Результат первого прогона пробы (2026-09-28): контроль провалился

Проба отработала быстро (`TIME t=4265 → t=5455`, ~1,2 с), но дала
`FBP-A FAIL` — а это **положительный контроль**:

```
FBP-A  sysmem->dmem ok  got=0x00000000 want=0xEC547D23  FAIL
FBP    VERDICT ctrlA=FAIL frtsRead=zero write=sent roundTrip=FAIL
```

### Что это значит

`ctrlA=FAIL` обесценивает **всё** C–G. Вывод «FB недоступен» из этого
прогона делать нельзя — промахнулся инструмент, а не железо. Скрипт
теперь печатает об этом явное предупреждение.

### Причина: ненулевое смещение окна DMEM в самой пробе

Первая версия читала в DMEM по `0x300`/`0x400`, передавая их вторым
аргументом `gsp_dma_transfer` (→ `DMATRFFBOFFS`). Ни один рабочий вызов
в коде так не делает — все используют `memOff = 0`, включая тот, чей
результат в логе совпадает:

```
DMA   dmem_hdr=0x00100001 want=0x00100001 OK      <- memOff = 0, работает
```

Окно DMEM на GSP не адресуется как обычное смещение. Проба переписана на
**единственное** окно `0x000` — для входа, выхода и обратного чтения.

### Побочная ошибка: проверка «есть ли данные» была фиктивной

`FBP-E ... crc32=0x38E3FFEE (has data)` — **ложь**. Критерий был
`(crc == 0) || (crc == 0xFFFFFFFF)`, а CRC32 четырёх килобайт нулей равен
ровно `0x38E3FFEE`: проверка объявляла «есть данные» на полностью нулевом
буфере. Теперь нулевой CRC считается на месте и печатается рядом.

### Побочная находка: `imemSec=1` **убивает весь DMEM**

Попытка FWSEC №2 (`sigIndex=1, imemSec=1`) даёт не отказ, а разрушение:

```
FWSEC ours FAIL ... dbg=0x007E0009
FWSEC   dmem[0x000]=0xDEAD5EC2
FWSEC   dmem[0x004]=0xDEAD5EC2      (512 слов подряд)
```

Весь DMEM заполняется `0xDEAD5EC2`. Secure-DMA на 70HX не просто
отклоняется ([§20](KNOWN-ISSUES.md)) — он **смывает DMEM целиком**.
Попытка бесполезна и вредна.

### Что осталось открытым

«Доступен ли кадровый буфер через GSP-DMA» — **по-прежнему открыт**.
Исправленная проба стоит ~2,5 минуты до ответа.

## 6. Шаг 1 — проба доступа к кадровому буферу (реализовано)

### 6.1 Почему старая проба ничего не значила

`test_fb_read()` в `src/unlock_v2.c` была написана как быстрая проверка гипотезы
«GSP-DMA умеет читать FB». Она дала `0x00000000 ×4`, и это было истолковано как
«FB недоступен». **Вывод был неверен**, потому что проба неконтролируемая:

| Дефект | Последствие |
|---|---|
| Нет положительного контроля | неизвестно, работает ли сам механизм чтения DMEM |
| Нет отрицательного контроля | «ноль» неотличим от «DMA молча не исполнилась» |
| Всего 16 байт | нулевой регион и нерабочий DMA дают одно и то же |
| Вызывается из `fwsec_boot_gsp_sig()` **после** неудачи FWSEC | GSP уже в грязном состоянии, DMEM переписан прогоном FWSEC — результат недостоверен |

### 6.2 Что сделано

Проба заменена на `fb_access_probe()` — самодостаточный диагностический блок
с контролями, запускаемый на **чистом** GSP до основного флоу:

| # | Тест | Что доказывает |
|---|---|---|
| A | чтение 256 Б из физического адреса собственного FWSEC-буфера | **положительный контроль** — механизм чтения работает; ждём `0xEC547D23` |
| B | чтение 256 Б из заведомо невалидного адреса | **отрицательный контроль** — как выглядит провал |
| C | чтение 256 Б с `0x1FFE00000` (FRTS) | доступен ли FRTS |
| D | чтение 256 Б с `0x1FFF00000` (`wprEnd`) и `0x100000000` (середина FB) | есть ли в FB хоть что-то непустое |
| E | CRC32 64 КБ с `0x1FFE00000` | заполнен ли регион целиком, а не только начало |
| F | **запись** паттерна в `0x1FFE00000` через GSP-DMA | можно ли писать в FB |
| G | **read-back** записанного | подтверждение round-trip |

Тесты F–G — главные: они дают **однозначный** ответ независимо от того, что
лежит в FB изначально. `WPR2` на этом этапе **не защёлкивается**, значит
регион не защищён и запись безопасна; при неудаче следующий POST всё очистит.

Безопасность соблюдает правило [KNOWN-ISSUES.md §22](../KNOWN-ISSUES.md):
все обращения к флешке — ровно один сектор; здесь обращений к флешке нет вообще.

Подробности реализации и порядок вызовов —
[70HX-NEXT-STEPS.md](70HX-NEXT-STEPS.md) §2.

## 7. Сравнение 90HX → 70HX

| Аспект | 90HX (GA102) | 70HX (GA104) |
|---|---|---|
| Объём FB | 10 ГБ | 8 ГБ |
| `frtsOffset` | `0x27FE00000` (в логе dmesg рабочей сборки) | `0x1FFE00000` (по формуле) |
| `WPR2` после анлока | `0x027FE000/0x027FEE00` | не встаёт |
| Образ FWSEC | `fwsec_ga102.bin` | `fwsec_ga104.bin` — **побайтово тот же файл** |
| Подпись FWSEC | `sig[2]` | `sig[2]` — **тот же файл** |
| `sig[0]` | — | 384 байта нулей |
| IMEM после POST | заполнен (была гипотеза §17) | **пуст** — гипотеза опровергнута |
| Secure-DMA в IMEM | SEC=1 работает | **отказ `0xDEAD5EC1`**, работает только SEC=0 |
| BAR'ы | 16 / 64 / 32 МБ | 16 / 64 / 32 МБ (то же) |
| Карт в системе | 1 | 2 (одна — «призрак» от прежней работы с 50HX) |
| Статус | **полный анлок, подтверждён** | эксплойт есть, WPR2 нет |

## Приложение: `TARGET PROFILE` — что и откуда берётся

Всё выводится из одного числа `TARGET_FB_SIZE`, поэтому профили не могут
разъехаться:

```
TARGET_FB_SIZE        = 0x200000000            (8 ГБ)  ← единственный ввод
  ↓
VGA_WS_OFFSET         = FB - PRAMIN(1 МБ)      = 0x1FFF00000
WPR_END               = VGA_WS & ~0x1FFFF       = 0x1FFF00000
FRTS_OFFSET           = WPR_END - FRTS(1 МБ)    = 0x1FFE00000
FRTS_OFFSET_PG        = FRTS_OFFSET >> 12       = 0x1FFE00
WPR2_LO               = FRTS_OFFSET >> 8        = 0x01FFE000   ← ЭКСТРАПОЛЯЦИЯ
WPR2_HI               = WPR2_LO + 0xE00         = 0x01FFEE00   ← ЭКСТРАПОЛИРОВАНИЕ
```

Компилятор проверяет выравнивание `FRTS_OFFSET` по 4 КБ и отсутствие
переполнения 32-битного окна `WPR2` — обе проверки ловят ошибку в профиле
до записи на флешку, а не на стенде.

Строки `WPR2_LO`/`WPR2_HI` — **единственные** в блоке, взятые не из формулы
драйвера, а из одного замера на 10-гигабайтной карте. Это причина №1
в [§5.3](#53-что-остаётся-как-причина).

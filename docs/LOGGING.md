# Raw-журнал UEFI-приложения

## Назначение

Журнал — главный источник аппаратной приёмки. Это не файл FAT32: приложение
пишет последовательные 512-байтные секторы в отдельную область USB, начиная с
LBA 4 000 000. Поэтому он доступен даже после сбоев файловой системы и не
попадает внутрь 256-МиБ релизного образа.

## Контракт записи

- начало содержит `CMPUNLOG v1` и профиль карты;
- текст хранится в ASCII; неподдерживаемые символы заменяются `?`;
- сектор считается действительным только после полной записи;
- последний незаписанный буфер теряется при выключении питания;
- завершённый прогон заканчивается `END   ---- end of log ----`.

`END` нельзя заменять промежуточным успехом. Лог с правильными SS/GFX строками,
но без финального `END`, считается оборванным.

### GR topology census

Сборка с `GR_TOPOLOGY=1` добавляет read-only формат `GRTOPOFMT 1`. Она
обязана содержать два полных блока:

```text
GRTOPO BEGIN PRE read-only
GRTOPO PRE FUSE ...
GRTOPO PRE EFFECTIVE ...
GRTOPO PRE PTOP ...
GRTOPO PRE GPC0 ...
...
GRTOPO PRE GPC5 ...
GRTOPO PRE CORR ...
GRTOPO END PRE
```

Второй блок имеет стадию `POST` и снимается перед финальным FLR. Наличие
`GRTOPOFMT 1` делает оба блока обязательными для `verify-log.ps1`; в обычном
release-логе без формата проверка остаётся необязательной. Эти строки
доказывают только прочитанные значения MMIO, но не исправность скрытых блоков.

### Read-only ReBAR probe

Сборка `REBAR_PROBE=1` добавляет формат `RBPROBE format=1`. Диагностика не
делает PCI/MMIO-записей и отсутствует вместе со строками маркеров в обычном
release-бинарнике. Полный блок имеет однозначные границы и стадии:

```text
RBPROBE BEGIN format=1 read-only ...
RBPROBE STATE ...
RBPROBE BRIDGE ...
RBPROBE APERTURE ...
RBPROBE VERDICT ...
RBPROBE END read-only
```

`STATE` содержит BAR1/BAR3, XVE `0x88724`, `0x88BBC`, `0x88BC0`, `0x88DCC`
и стандартную PCIe Extended Capability Resizable BAR. `BRIDGE` фиксирует
upstream bridge и его 64-битное prefetchable-окно. `APERTURE` перечисляет
дескрипторы `EfiMemoryMappedIO` и отдельно сообщает, покрывает ли один из них
8-ГиБ выровненный диапазон внутри окна моста.

`VERDICT CANDIDATE` означает только согласованность capability и адресного
окна; это не доказательство безопасной записи и не разрешение включать
`REBAR_EXPERIMENT`. При наличии `RBPROBE BEGIN` проверяющий требует ровно по
одному `BEGIN`, `BRIDGE`, `VERDICT`, `END` и полный набор стадий. В старых и
release-логах без `RBPROBE` проверка остаётся необязательной.

## Жизненный цикл

```powershell
out\reset-stick-log.ps1
# человек загружается с USB и ждёт возврата в Windows
out\pull-log.ps1 -Tag <метка>
out\verify-log.ps1 out\usb-log-<метка>.txt
```

`reset-stick-log.ps1` обязателен: запись нового `.img` не достигает области
журнала, и там остаётся корректный `END` предыдущей сессии.

`pull-log.ps1` сохраняет stdout `read-log.ps1`, включая сводку ключевых строк.
Поэтому отдельные строки встречаются в транскрипте дважды. Для подсчётов
используйте только тело между баннерами; `verify-log.ps1` делает это сам.

## Что доказывает журнал

Журнал может доказать, что конкретный профиль стартовал, достиг нужных стадий,
прочитал ожидаемые регистры и завершился. Он не доказывает сам по себе FPS,
CUDA throughput, видимость USB конкретной прошивкой или соответствие файла на
носителе образу — для последнего нужен `verify-image.ps1 -CompareOnly`.

Минимальные маркеры успешного release-прогона:

```text
CMPUNLOG v1 profile=CMP 70HX (GA104)
G2RMC ... already open 0 of 2
G2RMC ... already open 1 of 2
G2GFX ... GFX_SPEED_SELECT=0x00000004 SET
G2SUM ... readback 0x00000004 OK
END   ss0=0x88888888 ss1=0x00000008 PLM=0xFFFFFFFF
END   ---- end of log ----
```

## Синхронные изменения

При изменении формата или маркера одновременно обновляйте:

1. writer в `src/unlock_v2.c`;
2. `out/read-log.ps1` и `out/pull-log.ps1`;
3. критерии `out/verify-log.ps1`;
4. этот документ и `out/BUILDS.md` после аппаратной проверки.

Полное описание формата, указателей, кольца и исправленных ловушек сохранено в
[`history/LOGGING.md`](history/LOGGING.md).

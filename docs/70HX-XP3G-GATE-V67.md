# E-A — гейт XP3G привилегированным писателем V67

**Дата постановки:** 2026-10-09. **Статус: ВЕРДИКТ `OPEN` — гейт открыт.**
Програн на железе 2026-10-09, сборка `xgate` md5 `8a71435595182b208bea7fea5e9fcfd2`,
686 080 байт, лог `out/usb-log-xgate.txt`, время прогона 7879 мс.

## 0. РЕЗУЛЬТАТ (2026-10-09)

```
XGATE phase0: gate 0x0008E1B0=0xFFFFFF8F ctrl 0x0008E1B4=0xFFFFFFCF
XGATE phase0: XP3G OVR0=0x00000000 VAL0=0x00000000 OVR3=0x00000000 VAL3=0x00000000
XGATE phase1: target  0x0008E1B0 <- 0xffffffff gave 0xFFFFFFFF OPEN (polls=81, recheck=0xFFFFFFFF, before=0xFFFFFF8F)
XGATE phase2: control 0x0008E1B4 <- 0xffffffff gave 0xFFFFFFFF OPEN (polls=81)
XGATE VERDICT: OPEN - gate opens privileged; XP3G_OVR0/VAL0 writable next; PORT-STATUS 1s needs rework
```

**Привилегированный писатель V67 открывает гейт XP3G в точный `0xFFFFFFFF`.**
С хоста он не открывается ни одной записью из 36 (§1r) — это разные писатели.

| | |
|---|---|
| до | `0xFFFFFF8F` |
| после | `0xFFFFFFFF` |
| polls | **81** — запись асинхронная, ~81 мс |
| recheck через 0,5 с | `0xFFFFFFFF` — **встало и не слетело** |
| контроль `0x8E1B4` | `0xFFFFFFFF`, polls **81** — тот же механизм |
| цена | 2 975 748 мкс = 26 % прогона |

Одинаковые `polls=81` у цели и контроля — признак одного и того же механизма,
а не везения.

### 0.1 Независимое подтверждение, чужеродным кодом

В дереве **уже был** дамп `GEN2M after-unlock`, к E-A отношения не имеющий.
Он печатает семейство `0x88FF4/0x88FF8/0x88AB4/0x8E1B0`; `!` = не изменилось
от POST-замеренного значения, `*` = изменилось.

| лог | сборка | POST | after-unlock |
|---|---|---|---|
| `usb-log-1008-235743` | `unlock_v3r` (рабочая) | `0x8E1B0=0xFFFFFF8F!` | `0x8E1B0=0xFFFFFF8F!` |
| `usb-log-sel0x8-notset` | `gfxsel_0x8_oracle` | `0x8E1B0=0xFFFFFF8F!` | `0x8E1B0=0xFFFFFF8F!` |
| `usb-log-pre-xgate` | `gfxsel_0x8_oracle` | `0x8E1B0=0xFFFFFF8F!` | `0x8E1B0=0xFFFFFF8F!` |
| **`usb-log-xgate`** | **`xgate` (E-A)** | `0x8E1B0=0xFFFFFF8F!` | **`0x8E1B0=0xFFFFFFFF*`** |

Во всех прошлых прогонах гейт оставался `0xFFFFFF8F` после анлока. В прогоне
E-A он `0xFFFFFFFF`, помечен `*`, и **соседи `0x88FF4` / `0x88FF8` / `0x88AB4`
остались закрыты** — то есть открылся именно `0x8E1B0`, а не «всё семейство
разом». Это подтверждение из существующего измерителя проекта, а не из нового
кода.

Время: 7879 мс против 4870 / 4880 мс у рабочей сборки. Прирост **+2985 мс** —
это ровно цена двух ботер-циклов плюс два опроса по 81 мс и пауза 500 мс.
Цена предсказана заранее (~2,5 с) и совпала.

### 0.3 Что это меняет

§1s закрыл Gen2, потому что оставались два маршрута дороже результата:
реверс собственного V67 либо Windows-BYOVD. **Ни один не понадобился.**
Интерфейс блоба был уже известен проекту, требовалось сменить адрес.

Открытым остаётся ровно один вопрос, и он был назван в §1q до всяких
экспериментов: *«заливается ли policy set, когда гейт открыт»*. При
`0x8E1B0 = 0xFFFFFF8F` поле `XP3G_OVR0` (`0x8E110`) не вставало — это и был
провалившийся 7-й регистр из 7. Теперь гейт открыт, и следующий шаг (§5) —
проверить, что встают все семь.

**Линк в E-A не тронут.** Ни кика, ни TLS, ни ретрейна. Карта после прогона
осталась ровно в той же конфигурации, что и рабочая сборка, — Gen2 впереди.

## 1. Что именно проверяем

> Откроет ли **привилегированный** писатель V67 гейт `0x8E1B0` в точный
> `0xFFFFFFFF`, который с хоста не открывается **ни одной** записью из 36?

Это последний необходимый шаг к PCIe Gen2. Всё остальное по Gen2 уже измерено
и сделано — см. [`70HX-PORT-STATUS.md`](70HX-PORT-STATUS.md) §1o–§1s:

| факт | где |
|---|---|
| линк физически на Gen1: 3.343 GB/s, 83.6 % потолка Gen1 x16, `gen.current=1` под нагрузкой 11 из 11 | §1p |
| карта и слот способны Gen2 (`gen.max = 2`) — потолок не кремниевый | §1p |
| с хоста **не открывается ни одна маска из 36** — три прохода, ноль | §1r |
| привилегированный писатель есть, это V67 на RISC-V ядре SEC2 | §1q |
| 6 из 7 регистров политики xrip пишутся с хоста, седьмой (`XP3G_OVR0`) заперт гейтом `0x8E1B0 = 0xFFFFFF8F` | §1q |
| Gen2 закрыт по решению пользователя: оставались реверс V67 либо Windows-BYOVD | §1s |

## 2. Почему это НЕ повторение §1q / §1r

Отрицательный результат §1q/§1r честный, но он про **другого** писателя.
Там били `mmio_write32` **с хоста**, а маска и *есть* защита от такой записи —
вывод «0 из 36» верен для хоста и ничего не говорит о V67.

§1r это прямо оговаривает:

> *Это окончательно закрывает путь «открыть маску с хоста, потом писать
> политику». Одновременно это **не** закрывает Gen2: у нас уже есть
> привилегированный исполнитель (V67 открывает PLM), вопрос только в том,
> что именно он пишет.*

E-A — это ответ на «что именно он пишет», для одного адреса.

## 3. Примитив уже готов. Реверс блоба не требуется

V67 — **параметризованный** писатель, не непрозрачный кусок:

```
pv = payload+0xf948  ->  значение
pa = payload+0xf960  ->  адрес
```

Это зафиксировано в проекте двумя независимыми способами:

* комментарий `src/unlock_v2.c:5553-5554` (в коде, не в документации);
* работающие вызовы в дереве —
  `pcie_gen_unlock_debug()` пишет так же в `PCIE_FUSE_OVERRIDE` (`0x823810`),
  а `ftp_booter_write()` вообще параметризована как `write(addr, want, &polls)`.

Значит §1s указывает на более дорогой маршрут, чем нужно: **интерфейс блоба
проекту уже известен**, меняется только адрес.

### 3.1 Гейт уже есть в таблице

`0x8E1B0` с целевым значением `0xFFFFFFFF` **уже присутствует** в таблице
`g_rj16[]` (`src/unlock_v2.c:2471`):

```c
{0x00088ab4U,0xffffffffU},{0x0008e1b0U,0xffffffffU},{0x0008e1b4U,0xffffffffU},
```

Свип по `g_rj16` уже умеет писать эту запись привилегированно
(`*pv = g_rj16[i].val; *pa = g_rj16[i].addr; booter_load_v67(...)`).
Но свип выключен (`g_gen2Enable = FALSE`, `g_gen2Fire = FALSE`), и v3n/v3r
вырезали gen2-код.

**E-A намеренно НЕ включает свип целиком.** Причина — ловушка, которую надо
назвать, чтобы её не повторили: критерий завершения свипа требует точного `FF`
**по всем** записям таблицы, а

* `0x8E1DC` документирован как RO и точного `FF` не держит
  (`REGISTERS.md`, «НЕ держит точный FF — семейство живое/статусное»);
* блок OPTB `0x8200d0..0x8200f4` исключён (записи валят гостя в ресет, прогоны
  29–31), `0x88084` исключён (speed-ниббл живой, следует за линком).

То есть `done` не сбрасывается никогда, и включение свипа сожжёт 3 полных
прохода впустую. E-A делает **два точечных выстрела** вместо этого.

## 4. Фазы и почему они именно такие

Риск растёт строго по фазам; фаза 0 только на чтение идёт первой, чтобы даже
жёсткое зависание в фазе 1 оставило дамп в логе на флешке.

| фаза | что | риск |
|---|---|---|
| **0** | ТОЛЬКО ЧТЕНИЕ: `0x8E1B0..BC`, семейство, `XP3G` `OVR0`/`VAL0`/`OVR3`/`VAL3` | нулевой |
| **1** | **ЦЕЛЬ**: `0x8E1B0 ← 0xFFFFFFFF` привилегированно | снятие защиты с записи |
| **2** | **КОНТРОЛЬ**: `0x8E1B4 ← 0xFFFFFFFF`, тот же код, свой FLR-цикл | то же |

**Живой линк блок не трогает.** Нет ни кика `0x8872C`, ни TLS, ни ретрейна, ни
записей политики PCIe. Пишется только регистр-маска — то есть снимается защита
с записи, и ни одного функционального бита. Это ровно то, что §1q объявил
заранее перед шагом 1b.

**Цена:** два полных ботер-цикла, ~2,5 с к прогону (4,9 с).

Ограничение ботера — третий выстрел в одном состоянии SEC2 не работает
(v3.18), поэтому между фазами 1 и 2 обязателен свой FLR-цикл, как в
`ftp_booter_write()`.

### 4.1 Почему контроль обязателен

[`70HX-FINAL-SUMMARY.md`](70HX-FINAL-SUMMARY.md) §4: **«показание принято за
доказательство, не будучи им»** — три самые дорогие ошибки проекта были именно
такого рода.

Отрицательный результат фазы 1 сам по себе не значит ничего: он не отличает
«гейт особенный» от «механизм в этом прогоне не выстрелил». `0x8E1B4` — сосед
по тому же семейству `0x8E1B0..F0`, с тем же стоковым значением, и открывается
тем же кодом. Разбор только пары «цель + контроль»:

| контроль `0x8E1B4` | цель `0x8E1B0` | что это значит |
|---|---|---|
| `OPEN` | `OPEN` | **гейт открыт.** §1s пересмотреть, Gen2 жив, идти в §5 |
| `OPEN` | `NOT OPEN` | гейт особенный, не открывается. Отрицательный результат **заслуженный** |
| `NOT OPEN` | — | **результат фазы 1 НЕДЕЙСТВИТЕЛЕН.** Закрывать Gen2 по нему нельзя, надо разбираться с механикой |

## 4a. ЭКСПЕРИМЕНТ E-B — ПОЛИТИКА ЗАЛИВАЕТСЯ. РЕЗУЛЬТАТ

Прогон 2026-10-09, сборка `xgate2` md5 `9832745e50ee02cff08ec8d0c8cc5c45`,
688 640 байт, лог `out/usb-log-xg2.txt`, 7849 мс.

```
XGPOL precondition: XP3G gate 0x0008e1b0 = 0xFFFFFFFF OPEN
XGPOL XP3G_OVR0 0x0008E110 before=0x00000000 want=0x00000001 CHANGE
XGPOL XP3G_OVR0 0x0008E110 wrote 0x00000001 got 0x00000001 STUCK
XGPOL summary: 5 of 5 changed fields stuck (2 NOOP not counted)
XGPOL VERDICT: POLICY-OK
```

**Вопрос, который §1q назвал до всяких экспериментов, закрыт: при открытом
гейте policy set заливается.**

| было (§1q, гейт закрыт) | стало (E-B, гейт открыт) |
|---|---|
| **6 из 7** полей вставали | **5 из 5** значимых встают |
| `XP3G_OVR0` (`0x8E110`) — `*** НЕ ВСТАЛО ***` | `XP3G_OVR0` — `STUCK` |

Продавленное в §1q поле — то самое, ради которого Gen2 был закрыт в §1s.

### 4a.1 Почему 5, а не 7 — и почему это важно

Два поля помечены `NOOP` и **в счёт пройденных не идут**:

| поле | before | want | почему NOOP |
|---|---|---|---|
| `XP3G_VAL0` `0x8E120` | `0x00000000` | `0x00000000` | уже было нулём |
| `PL_LINK_RATE` `0x8C1C0` | `0x00140000` | `0x00140000` | **изменилось после E-A**, в §1q было `0x00060000` |

Это ровно та ловушка, что описана в `70HX-FINAL-SUMMARY` §4, ошибка №1:
«`is_unlocked()=1` — функция перечитывает регистры, в которые код только что
записал. Тавтология». Поле, у которого цель совпала с «до», ничего не доказывает
и по построению всегда даёт «успех». Без защиты от этого E-B отчитался бы
«7 из 7» с двумя фиктивными проходами.

### 4a.2 Линк не тронут

```
XGPOL link BEFORE: LNKSTA=0x11010040 speed=1 width=4
XGPOL link AFTER : LNKSTA=0x11010040 speed=1 width=4
```

Побитово идентично, `speed=1` (Gen1) — как и был.

### 4a.3 Побочное наблюдение, которое стоит держать в голове

В дампе `GEN2M after-unlock` этого прогона впервые видно **семейство открытым
частично**, а не «три маски, которые всегда были открыты»:

```
[ 0.. 3] 0x00823804=0xFFFFFFFF* 0x00088FE8=0xFFFFFFCF! 0x00088FEC=0xFFFFFFCF! 0x00088FF0=0xFFFFFFCF!
[ 4.. 7] 0x00088FF4=0xFFFFFF8F! 0x00088FF8=0xFFFFFF8F! 0x00088AB4=0xFFFFFF8F! 0x0008E1B0=0xFFFFFFFF*
[ 8..11] 0x0008E1B4=0xFFFFFFFF* 0x0008E1B8=0xFFFFFFCF! 0x0008E1BC=0xFFFFFFCF! 0x0008E1C0=0xFFFFFFCF!
[16..19] 0x0008E1D4=0xFFFFFFFF* ... 0x0008E1DC=0xFFFFFF8F!
[20..23] ... 0x0008E1F0=0xFFFFFFFF*
```

`*` теперь стоит на `0x8E1B0`, `0x8E1B4` **и** `0x8E1F0` — то есть привилегированный
писатель меняет состояние, которого не менял ни один предыдущий прогон, и
соседние регистры семейства остаются закрытыми. Это независимая проверка
адресности: пишется ровно запрошенный адрес.

### 4a.4 Регрессий нет

`already open 0 of 2` / `1 of 2` без `iter 2`, `GFX gates open 2 of 2`,
`GFX_SPEED_SELECT=0x00000004 SET`, `END ss0=0x88888888 ss1=0x00000008
PLM=0xFFFFFFFF`, маркер конца лога на месте.

Время: 7849 мс. E-B добавил **31 мкс** — семь MMIO-записей, как и ожидалось.
Время прогона целиком определяется E-A (2 972 568 мкс, 26 %).

### 4a.5 Что осталось

Ровно одно действие, и оно **впервые трогает живой линк**:

| шаг | что | чем | где брать |
|---|---|---|---|
| 1 | кик LTSSM **последним**, после всех записей | BAR0 `0x8872C = 6` | уже есть в дереве |
| 2 | `TLS = 2` на GPU | PCI config `cap+0x30.w` | §1p ошибка 2: через BAR0 `0x880A8` отбрасывается |
| 3 | `TLS = 2` на root port | PCI config `cap+0x30.w` | там же |
| 4 | retrain | root port `+0x10.w \|= 0x20` | §1p |

Известные границы, чтобы не тратить время:

* `LINK_CAP` (`0x88084`) **не писать** — xrip его не пишет, и `speed`-ниббл
  живой: следует за фактическим линком, кремний клампит Gen3
  (`write 03 → readback 02`, `REGISTERS.md`).
* Gen3/Gen4 целью не является: кламп тот же, и на 40HX эта граница исследована
  до конца (`PCIE_GEN3_CMP40HX_RESEARCH.md`).
* `TLS` через BAR0 не работает под живым GSP — только PCI config.

**Критерий Gen2 — единственный честный:** `src/tools/pcie-bw.py` даёт
**> 5,5 GB/s** против нынешних 3,343. `nvidia-smi --query-gpu=pcie.link.gen.current`
критерием **не является** — это downshift в простое (§1p шаг 0.1).

Риск шага 1 — единственный в проекте, где возможна потеря `nvidia-smi`:
на 40HX Link Disable отрывал GSP/RM, но здесь шаг нормальный (ре-train
без Disable) и применяется на живом линке. Откат — перезагрузка с флешки.

## 4a.6 ЭКСПЕРИМЕНТ E-D — ПРИЧИНА НАЙДЕНА: `CapPtr` ОБНУЛЁН. 2026-09-09

Сборка `xcap` md5 `57ccd378b1822cbd195c53a1f0c3814d`, лог `out/usb-log-xcap.txt`.
**Только чтение**, ни одной записи.

```
XCAP env: gRbAllN=1 gBrIdx=0 GPU bus=2 dev=0 fn=0
XCAP raw GPU/gRb id=0x248A10DE 0x04=0x00100006 CapPtr=0x00 capLo=0x06
XCAP RESULT GPU/capptr -> 0 (steps=0 lastid=0x00)
XCAP walk GPU/from40 step 0 pos=0x40 id=0xDE next=0x10
XCAP walk GPU/from40 chain ends after 1 steps, no id=0x10
XCAP raw BRIDGE id=0xA1678086 0x04=0x00100007 CapPtr=0x00 capLo=0x07
XCAP RESULT BRIDGE/gBr-from40 -> 64 (steps=1 lastid=0x10)
```

| гипотеза | вердикт |
|---|---|
| (A) чтение `0x04` отдаёт `0xFFFFFFFF` | **отпадает** — читается `0x00100006` |
| (B) `CapPtr = 0` | **ПОДТВЕРЖДЕНА** |
| (F) `gRb` ≠ тот RB, под которым устройство найдено | **отпадает** — `gRbAllN=1`, `GPU/rb0` отвечает тем же |

**На GPU цепочки PCIe capabilities нет.** Байт `0x07 = 0x00`. Обход с `0x40`
читает мусор: `id=0xDE` на позиции конфига — это BAR4, а не capability.

**На мосте capability есть**, лежит ровно на `0x40` (`id=0x10`), но указатель
на неё **тоже обнулён**. То же самое, что и на GPU: capability присутствует в
hardware, а вот указателя нет.

Побочно: это объясняет, почему `GEN2C` показывал `not found` во **всех** шести
прогонах проекта — сломан не обход, а данные.

## 4a.7 ЭКСПЕРИМЕНТ E-E — ЗЕРКАЛО LC2 ЗАБЛОКИРОВАНО. ГИПОТЕЗА НЕ ПОДТВЕРДИЛАСЬ

Сборка `xtls` md5 `a68fda6dfc22774e6cd971bb6f717c7d`, лог `out/usb-log-xtls.txt`.

Гипотеза была: запись в `0x880A8` отбрасывалась при **закрытом** гейте (§1p
ошибка 2); гейт с тех пор открыт (E-A) — проверим, изменилось ли.

```
XTL precondition OK: gate open
XTL LC2_TLS 0x000880A8 before=0x00000001 want=0x00000002 CHANGE
XTL LC2_TLS 0x000880A8 wrote 0x00000002 got 0x00000001 DROPPED
XTL LINK_CONFIG 0x0008C040 before=0x80085800 want=0x80085800 NOOP
XTL PL_LINKRATE 0x0008C1C0 before=0x00140000 want=0x00140000 NOOP
XTL link AFTER : LNKSTA=0x11010040 speed=1 width=4
XTL summary: 0 of 1 changed fields stuck (2 NOOP not counted)
XTL VERDICT: MIRROR-BLOCKED - the gate was not the reason the BAR0 mirror refused writes
```

**Гипотеза не подтвердилась: гейт `0x8E1B0` не имеет отношения к `0x880A8`.**
`0x8E1B0` — PLM блока XP3G, а LC2 живёт в другом защищённом домене.

### Что этот прогон всё-таки доказал, и это важнее отказа

Контрольные поля стоят **ровно на цели, записанной в E-B**. То есть хостовые
записи в BAR0-привилегированный домен **проходят** — `0x8C040` и `0x8C1C0` были
записаны именно в E-B, и здесь они держатся. Три `PLM = 0xFFFFFFFF` тоже
встали. Значит блокировка **избирательная**, а не доменная: домен открыт,
заблокирован конкретный регистр.

`LNKSTA` до и после побитово идентичен, `speed=1`. Откат не потребовался — и он
не потребовался бы в любом случае: линок переходит на новую скорость только по
ретрейну, а ретрейна здесь не было.

## 4a.8 СТРУКТУРНЫЙ ВЫВОД: Gen2 НА ЭТОМ ПУТИ ЗАКРЫТ

> ## ⚠ ВЫВОД ОПРОВЕРГНУТ 2026-10-10, измерением. Не читать как установленный факт.
>
> Первая посылка этого раздела — «на GPU цепочки PCIe capabilities нет,
> `CapPtr = 0`» — **ложна. Это баг в нашем же коде**, а не свойство карты.
> Замерено через WinRing0 из Windows: `CapPtr` лежит по адресу **`0x34`**, а
> `find_pcie_cap()` (`src/unlock_v2.c:1513-1515`) берёт его из байта `0x07`
> dword'а по `0x04`. Байт `0x07` — старший байт **Status**, он по спецификации
> всегда 0. Обход цепочки не мог начаться **никогда**, ни на одной карте, ни в
> одном прогоне.
>
> Цепочка есть и обходится:
>
> ```
> GPU 01:00.0  CapPtr=0x60
>   0x60 PM -> 0x68 MSI -> 0x78 PCIe -> 0xB4 Vendor -> 0x00
> ```
>
> Вторая посылка — «`GEN2C ... pcie_cap not found` подтверждает отсутствие» —
> тем более ничего не доказывает: она наблюдает **тот же** баг.
>
> Разбор замера, новая находка про `LNKCAP` и то, что осталось открытым, —
> [§4a.11.8](#4a118-замер-config-space-2026-10-10-вывод-4a8-опровергнут).

Это не «ещё не нашли способ», а структурный факт:

| | PCI config capability | BAR0 `0x880A8` | вывод |
|---|---|---|---|
| **GPU** | **отсутствует** (`CapPtr=0`; обход с `0x40` даёт BAR4) | заблокирован (не гейтом `0x8E1B0`) | **обе двери закрыты** |
| **мост** | есть на `0x40`, указатель обнулён | — | управляема |

Поставить TLS на GPU **ни одним** из двух путей нельзя тем, что есть в дереве.
Дальше нужна новая техника, а не новая ручка сборки.

Почему это не откладываем:

* маршрут был один, и он исчерпан намерно;
* обе гипотезы, которые его питали («нужен реверс V67», «нужен BYOVD»), сняты
  замерами — а исчерпание самого маршрута не ожидание;
* практическая польза Gen2 при одной карте с моделью целиком в VRAM мала по
  §1s: выигрыш только на загрузке модели и offload, не на `pp512`/`tg16`.

Что осталось бы делать, если задачу всё же поднимут заново — новая техника, а
не новый патч существующего:

| кандидат | суть | цена |
|---|---|---|
| запись в конфиг capability через другой транспорт | нужен доступ к config space помимо `Pci.Read` | неизвестна |
| поиск другого зеркала LC2 в BAR0 | `0x8Exxx`/`0x88xxx` уже сканируются дампами, но целенаправленно не искалось | дёшево, но шанс невелик: `0x880A8` — известное зеркало |
| BootROM/FPGA-уровень | состояние до POST | несопоставимо с текущим подходом |

Пока ни один из них не опробован, и **ни один не является выводом** — это
список идей, а не план. Планом это станет только после того, как будет выбран
и обоснован один.

> **Сноска, добавлена 2026-10-10. Вердикт выше не переписывается** — замеры
> E-D/E-E верны. Но кандидат №1 сформулирован слишком узко, и есть основания
> думать, что «другой транспорт» вообще не нужен, а нужен другой **момент
> времени**. Разбор — в [§4a.11](#4a11-что-даёт-референс-с-работающим-gen2).
> Ключевое наблюдение: `CapPtr = 0` зафиксирован и на GPU, **и на мосте** —
> при том что сама capability на мосте физически лежит по `0x40`
> (`XCAP RESULT BRIDGE/gBr-from40 -> 64`). Цепочка capabilities собирается
> прошивкой при инициализации устройства, и в нашем окне EFI она не собрана.
> Это не свойство карты.

## 4a.9 ЭКСПЕРИМЕНТ E-F — Host2Jtag НА GA104 ОТСУТСТВУЕТ. 2026-10-10

Сборка `xpjt` md5 `2f6f140069b0be6059e64c1d7f77cc64`, лог `out/usb-log-xpjt.txt`.
**Только чтение**, ни одной записи.

Идея: не переносить адрес, а искать **класс**. Замаскированный PLM-регистр в
этом проекте предсказуем — читается как `0xFFFFFF8F` / `0xFFFFFFCF`, открытый
как точный `0xFFFFFFFF`. Кандидат находится признаком.

Источник подсказки: `amoghmunikote/cmpunlocker` (CMP **170HX**) перечисляет
`JTAG (Host2Jtag register access): Working` и даёт `pjtag_plm = 0x0000c840`,
`pjtag_sec_plm = 0x0000c848`. Оговорка напечатана в лог: 170HX — это **GA100**,
у нас **GA104**, priv-домены между ними переставляются.

```
XPJT win   0x0000C800..0x0000C8FF: nonff=0 mask8f=0 maskcf=0 zeros=0
XPJT scan  0x000C0000..0x000C0FFF: nonff=0 mask8f=0 maskcf=0 zeros=0
XPJT xp3g  0x008E0000..0x008E0FFF: nonff=0 mask8f=0 maskcf=0 zeros=0
XPJT priv  0x00820000..0x00821FFF: nonff=7 mask8f=6 maskcf=4 zeros=448
XPJT printed 10 candidates (cap 160)
```

**Три окна из четырёх вернули полный ноль.** Окно `0xC8xx`, где у GA100 живёт
PJTAG, на GA104 пусто. Значит это не «адрес другой у GA100», а **регистра на
карте нет**.

### Что нашлось — и это не PJTAG

```
0x008200D0=0xFFFFFF8F  0x008200E0=0xFFFFFF8F
0x008200D4=0xFFFFFFFC  0x008200E4=0xFFFFFF8F
0x008200D8=0xFFFFFF8F  0x008200E8=0xFFFFFFFC
0x008200DC=0xFFFFFF8F  0x008200EC=0xFFFFFFFC
0x008200F0=0xFFFFFFFC  0x008200F4=0xFFFFFF8F
```

Десять регистров OPTB — те самые, которые проект исключает **не** из-за
неизвестности, а потому что записи в них валят гостя в ресет (прогоны 29–31,
три подряд).

Побочно: в priv-окне впервые виден класс `0xFFFFFFFC` (заперты биты 0,1) —
четыре регистра, которых в прежних выборках не было. Раньше встречались только
`0xFFFFFF8F` и `0xFFFFFFCF`. Это не JTAG, и лезть в них без причины не надо.

### Вердикт по треку B

| вопрос | ответ |
|---|---|
| есть ли PJTAG на GA104 | **нет** — окно `0xC8xx` пусто, признака ноль |
| есть ли он в другом месте BAR0 | нет — `0xC0xxx` тоже пусто |
| есть ли рядом новые запертые гейты | нет — кроме десяти уже известных OPTB |
| снимает ли Host2Jtag потолок доступа | **не на этой карте** |

Закрыто **замерено**, а не предположено. Осторожность оправдалась: перенос
`0xC840` вслепую не дал бы ничего.

Регрессий нет: `already open 0 of 2` / `1 of 2`, `GFX gates open 2 of 2`,
`GFX_SPEED_SELECT=0x00000004 SET`, `readback HELD`, `END ss0=0x88888888
ss1=0x00000008 PLM=0xFFFFFFFF`. E-F добавил **6,9 мс** (6919 мкс на четыре
дампа), прогон 4888 мс — обычные 4,9 с.

## 4a.10 ЭКСПЕРИМЕНТ E-G — ГРАНИЦЫ БЛОКА ОПТИМОВ. 2026-10-10

Сборка `xfcc` md5 `4997adc06d4fca10db01ce8d933b01d6`, лог
`out/usb-log-xfcc.txt`, 4880 мс. **Только чтение.**

Находка E-F: в priv-окне впервые встретился класс `0xFFFFFFFC` (заперты биты
0,1) — раньше были только `0xFFFFFF8F` и `0xFFFFFFCF`.

### Что вскрыли границы блока

```
XFCC edge before: 0x008200C8=0xBADF5040  0x008200CC=0xBADF5040
XFCC edge after : 0x008200F8=0xFFFFFFFF  0x008200FC=0xFFFFFFFF
```

`0xBADFxxxx` — маркер проекта: *«`0xBADF` = заперто»*. Слева **ещё один
защищённый домен**, справа **уже открытые** регистры. Значит блок
`0x8200D0..0xF4` — не «случайный набор», а ровно десять регистров **между
двумя доменами**.

### Два класса защиты

| класс | заперты биты | сколько | где |
|---|---|---:|---|
| `0xFFFFFF8F` | 4, 5, 6 | 6 | `D0 D8 DC E0 E4 F4` |
| `0xFFFFFFFC` | 0, 1 | 4 | `D4 E8 EC F0` |

`census` подтвердил, что это система, а не совпадение:
`opened=7 fcff=4 mask8f=6`, причём **`maskcf=0`** — в этом окне класса `CF` нет
вовсе.

### Снятие защиты — полное, а не частичное

```
XFCC census 0x008e1b00..0x008e1c00: opened=0 fcff=0 mask8f=0 maskcf=0
```

В XP3G-окне, где гейт `0x8E1B0` **уже открыт** (E-A), в этом диапазоне нет ни
одного `0xFFFFFFxx` — все регистры нулевые. То есть при открытии защита
снимается **целиком**, а не по битам.

### Вердикт

Гипотеза подтвердилась **в проверяемой части**: `0xFFFFFFFC` — настоящая маска с
отдельной семантикой битов, а не статусное поле.

Гипотеза **не подтвердилась** в части «их можно открыть»: записи в этот блок
валят гостя в ресет (прогоны 29–31, три подряд). Они заперты намерно, и цена
ошибки — ресет. **Открывать нельзя.**

Что изменилось в знании: раньше про эти десять было известно ровно одно — «не
трогать». Теперь — что это **система из двух классов защиты на границе
доменов**, один из которых (`0xFC`) в проекте не встречался нигде, и что
открытие гейта снимает защиту полностью.

Регрессий нет: `already open 0 of 2` / `1 of 2`, `GFX gates open 2 of 2`,
`GFX_SPEED_SELECT=0x00000004 SET`, `readback HELD`, `END ss0=0x88888888
ss1=0x00000008 PLM=0xFFFFFFFF`. E-G добавил **~7 мс**, прогон 4880 мс — обычные
4,9 с.

## 4a.11 Что даёт референс с работающим Gen2

Разбор материала `iatethelogs/cmp90hx_pwner` (CMP 90HX, GA102, Linux) — единственного найденного инструмента, где PCIe Gen2 **реально работает**. Разобран отдельно от §4a.8; ничего из §4a.9-4a.10 не опровергается.

### 4a.11.1 Оба рабочих референса делают Gen2 не из EFI

Главное наблюдение, и оно не про регистры.

| референс | где делает | чем | доступ к config space |
|---|---|---|---|
| **iatethelogs/cmp90hx_pwner** | **после** загрузки ОС, из Linux | `setpci` | config space = обычный файл `/sys/bus/pci/devices/*/config` |
| **xrip/cmp50hx-unlock** (см. `vendor/`) | **после** загрузки ОС, из Windows | BYOVD + задача входа в систему, `50HXInstaller.exe -gen2` | подписанный `.sys` |

Оба работают **после передачи управления ОС**; ни один не пытается делать Gen2 из EFI-стадии. Мы строили ровно наоборот: `phase3` (`src/unlock_v2.c:14477`) расположен до хендофа, и именно там, в нашем окне, E-D намерил `CapPtr = 0`.

### 4a.11.2 Что именно мы намерили, и почему это подозрительно

```
XCAP raw GPU/gRb id=0x248A10DE 0x04=0x00100006 CapPtr=0x00 capLo=0x06
XCAP RESULT GPU/capptr -> 0 (steps=0 lastid=0x00)
XCAP walk GPU/from40 chain ends after 1 steps, no id=0x10

XCAP raw BRIDGE id=0xA1678086 0x04=0x00100007 CapPtr=0x00 capLo=0x07
XCAP RESULT BRIDGE/gBr-from40 -> 64 (steps=1 lastid=0x10)
```

Ключевое — **вторая пара строк**. На мосте `CapPtr = 0x00` тоже, но capability там физически **есть**, по `0x40`, id `0x10`, и обход находит её с нуля. Устройство имеет capability, а указатель на неё не выставлен. Это не свойство карты — это состояние, в котором прошивка ещё не собрала цепочку.

Цепочка PCIe capabilities выстраивается платформенной прошивкой при инициализации устройства, а не зашита в кремний. Наш момент времени — ранняя стадия загрузки с USB-носителя, до инициализации графики.

**Гипотеза (проверяемая, дешёвая).** `CapPtr = 0` на GPU — артефакт **окна EFI**, а не отсутствие capabilities. Если так, маршрут не исчерпан: он работает, но не в том окне, где мы его пробовали, — и это совпадает с обоими референсами.

Гипотеза **не проверена** и может быть ложной: `_capptr = 0` бывает и настоящим свойством SKU. Разница решается одним чтением.

### 4a.11.3 Тест: одно чтение, без сборки и без прошивки

Снять dword по `0x04` у GPU из **уже загруженной Windows** (карта на месте, анлок с флешки отработал) и сравнить с `0x00100006` из `out/usb-log-xcap.txt`.

| результат | вывод |
|---|---|
| `CapPtr != 0` | гипотеза подтверждена. §4a.8 переоткрывается целиком; маршрут — post-OS config space, совпадает с обоими референсами |
| `CapPtr = 0` и в Windows | гипотеза опровергнута, `Cap = 0` — свойство SKU. Кандидат №1 остаётся, но «другой транспорт» не поможет |

Инструмент — `RWEverything` / `PCIeTool` / любой сторонний, что есть на машине. Штатного Windows-инструмента в дереве нет, и писать свой не нужно: это разовое чтение. Существующий `out/cudaprops.exe` конфиг не читает.

**Не надо** перепрошивать флешку ради этого замера.

### 4a.11.4 Рецепт референса целиком

Собран из `rejoin17-apply-all.sh` + `rejoin16-cycle.sh`:

| шаг | чем | BAR0? |
|---|---|---|
| открыть `0x823800` (FEAT PLM) | `rejoin16-cycle.sh` через ботер | да |
| открыть `0x88FE8` (XVE/LTSSM) | там же | да |
| целевая скорость | `setpci CAP_EXP+2c.w=0x0002` | **нет** |
| ретрейн | `setpci CAP_EXP+10.w \|= 0x20` с апстрим-моста | **нет** |
| повтор | до 13 попыток, пауза `0/0.25/0.5/1/2/3/5/8/13` с | — |

Два вывода, важных для нас.

1. **BAR0-зеркало `0x880A8` референсу не нужно вообще**: нет ни кика `0x8872C`, ни policy set из семи полей. Значит вердикт E-E (`MIRROR-BLOCKED`) — помеха конкретной доставке TLS, а не препятствие Gen2 как таковому. На config-маршруте заблокированное зеркало не нужно ровно потому, что нужно не оно.
2. **Его `TLS` не пишется вовсе**: `CAP_EXP+2c` — это `PCI_EXP_LNKCAP2`, read-only. Работает только `Retrain Link` с моста. Значит утверждение «`TLS=2` обязателен» **не подтверждено ни одним из двух референсов**, и это ещё одна причина не считать его условием, пока не будет своего замера. Разбор офсетов — `KNOWN-ISSUES.md` §51.5.

### 4a.11.5 Список масок для возвращаемой стадии

`{0x823800, 0x88FE8}` — две маски, больше ничего. Адреса `0x8E1xx` референс не трогает нигде. Это расходится с предписанием в комментарии `src/unlock_v2.c:5725` («вернуть эти 17 адресов ПЕРВЫМИ»); комментарий приведён в соответствие, **код не менялся**. Разбор — `KNOWN-ISSUES.md` §51.7.

`0x88FE8` сейчас не открывается нигде: выброшен из таблицы рендера в v3.40 как
«PCIe-домен», и с тех пор Gen2-домен не трогался.

**ХОСТ-MMIO НЕ БЕРЁТ — ПРОВЕРЕНО НА ЖЕЛЕЗЕ 2026-10-10.** Стадия E-F (`xgate4`,
§4a.11.12) открывала `0x88FE8` и четыре соседних адреса прямой записью MMIO
после гейта `0x8E1B0`, с опросом 400 мс. Все пять остались закрыты:
`0xFFFFFFCF` / `0xFFFFFF8F`.

**ЧТО ЭТО НЕ ОПРОВЕРГАЕТ.** Ни рецепт референса, ни саму маску: адрес
открывается ботером, а не хостом. Гейт `0x8E1B0` открывается ботером, и
хост-MMIO в него не пишет — значит и в `0x88FE8` без открывающего гейта
хостовая запись обречена. Проверка ботерного пути — E-G (`xgate5`).

**ЧТО ТУТ НЕ ДОКАЗАНО.** Ни то, что маска на GA104 не открывается вовсе, ни то,
что список `{0x823800, 0x88FE8}` нерабочий. Известен ровно один отрицательный
результат — хост-MMIO. Список остаётся верным описанием рецепта
iatethelogs; рабочим он будет или нет, покажет E-G.

### 4a.11.8 Замер config space 2026-10-10 — вывод §4a.8 опровергнут

Доступ получен. Не через `RWEverything` (GUI), а через `WinRing0x64.sys` из
древа xrip — ABI взят не с нуля, а из его же рабочего кода
(`efi-unlock-windows/tools/50hxcore/regs.go`, `PciRd`/`PcieCap`). Инструмент
в проекте: `src/tools/pci-config-dump.py`. Драйвер ставится как служба и после
чтения удаляется; на систему ничего не остаётся.

#### Что найдено

```
GPU 01:00.0 (10DE:248A)
0x04 : Command=0006  Status=0010     Status[4] Capabilities List = ЕСТЬ
0x34 : CapPtr = 0x60                 <- правильный адрес
цепочка: 0x60 PM -> 0x68 MSI -> 0x78 PCIe -> 0xB4 Vendor -> 0x00
```

```
Bridge 00:1b.0 (8086:A167)  CapPtr=0x40
цепочка: 0x40 PCIe -> 0x80 MSI -> 0x90 BridgeSubsys -> 0xA0 PM -> 0x00
```

**Цепочка capabilities есть на обеих сторонах и обходится полностью.**

#### Ошибка в нашем коде

```c
/* v2.99i FIX: CapPtr — байт 0x07 (старший байт dword@0x04);
 * раньше брали >>8 (байт 0x05) и всегда промахивались */
pos = (pci_cfg_rd_bdf(bus, dev, fn, 0x04) >> 24) & 0xFF;
```

| офсет | что там по спецификации |
|---|---|
| `0x04`-`0x05` | Command |
| `0x06`-`0x07` | **Status** (бит 4 = Capabilities List) |
| `0x08` | Revision ID |
| **`0x34`** | **Capabilities Pointer** |

Байт `0x07` — старший байт Status, зарезервированный и всегда нулевой. Отсюда
и `CapPtr = 0`, и «chain ends after 1 steps» в E-D, и `pcie_cap not found` во
всех шести прогонах `GEN2C`. Комментарий «v2.99i FIX» исправлял один сдвиг на
другой, но исходная посылка — «CapPtr входит в dword по `0x04`» — была неверна,
и потому чинилась не туда.

Побочно: у GPU есть **vendor-specific capability по `0xB4`**, о которой проект
не знал. Ещё один аргумент за то, что E-D читал мусор.

#### Новая находка, которой раньше не было: `LNKCAP` устройства

```
GPU      +0x0C LNKCAP = 0x00453D01   Max Link Speed [3:0] = 1  (2.5 GT/s)
         +0x12 LNKSTA = 0x00001101   Current = 1  Width = 16
         +0x30 LNKCTL2= 0x00000001   TLS = 1

Bridge   +0x0C LNKCAP = 0x11717C13   Max Link Speed [3:0] = 3  (8.0 GT/s)
         +0x30 LNKCTL2= 0x00010001   TLS = 1
```

`Supported Link Speeds` в `LNKCAP` — по спецификации HwInit, то есть не
меняется софтом. **Но на карте оно не обязано совпадать с тем, чем
реально торгует контроллер линка** — расхождение с BAR0-зеркалом (§4a.11.10)
и есть свидетельство, что может не совпадать. Обе стороны конфигурации
теперь известны:

| | Max Link Speed | вывод |
|---|---|---|
| GPU | **1** (2.5 GT/s) | устройство заявляет только Gen1 |
| мост | **3** (8.0 GT/s) | хост готов хоть до Gen3 |

Это независимо подтверждает `Device Max = 1` из NVML (§4a.11.7) — двумя
разными путями, из конфига и из драйвера.

**Почему это НЕ закрывает Gen2 окончательно.** `REGISTERS.md` фиксирует BAR0
зеркало `0x88084 LINK_CAP = 0x00453D02` — nibble **2**, тогда как конфиг даёт
`0x00453D01`, nibble **1**. Значения различаются ровно одним битом в поле
скорости. Возможны три прочтения, и различить их можно только замером:

| прочтение | следствие |
|---|---|
| `0x88084` отражает **фактический** линк, а не HwInit | тогда `...02` означает, что в какой-то момент линок **был** Gen2 |
| зеркало ** writable**, и LNKCAP в зеркале приоритетнее | тогда Gen2 достижим, и `0x88084` — рычаг |
| это разные регистры, и правит конфиг | тогда Gen2 недостижим |

Третий вариант согласуется с записью из проекта: `0x88084` писали (`write 03 →
readback 02`), то есть зеркало как минимум не полностью RO.

#### Что это меняет для маршрута

Список кандидатов §4a.8 **пересматривается целиком**:

* кандидат «конфиг через другой транспорт» — **снят**: транспорт есть, цепочка
  есть, `TLS`/`Retrain` писать можно;
* кандидат «другое зеркало LC2 в BAR0» — **остаётся и становится основным**,
  потому что `0x880A8` заблокирован (E-E), а `0x88084` выглядит доступным;
* остальные два не трогаем.

#### Чего здесь нет

Замеров не делалось **ничего, кроме чтения**. Ни одного байта в config space и
ни одного в BAR0 не записано. `WinRing0` в этом прогоне использовался только
на чтение. Проверка гипотезы про `0x88084` требует записи и отдельного
согласования — это следующий шаг, а не результат этого.

#### Самопроверка правки, 2026-10-10

`find_pcie_cap-selfcheck.py` прогоняет обе реализации обхода по одним и тем же
данным, снятым с карты:

```
GPU 01:00.0
  OLD (CapPtr из байта 0x07 dword@0x04)
      обход не начался: CapPtr вне диапазона 0x40..0xFF
      РЕЗУЛЬТАТ: PCIe capability НЕ найдена
  NEW (CapPtr из 0x34)
      0x60 PM -> 0x68 MSI -> 0x78 PCIe -> 0xB4 Vendor
      РЕЗУЛЬТАТ: PCIe capability найдена по 0x78
  ИТОГ: NEW находит capability — правка верна

Bridge 00:1b.0
  OLD -> обход не начался
  NEW -> 0x40 PCIe -> 0x80 MSI
  ИТОГ: правка верна
```

Ровно то поведение, которое было видно в прогонах: OLD не находит ничего, NEW
находит capability. Правка подтверждена на обеих сторонах линка, не только на
GPU.

#### Правка внесена

`src/unlock_v2.c`, функция `find_pcie_cap()`:

```c
pos = pci_cfg_rd_bdf(bus, dev, fn, 0x34) & 0xFF;   /* было: (rd(0x04) >> 24) & 0xFF */
```

Комментарий на месте старого «v2.99i FIX» переписан: он объяснял неверную
посылку («`CapPtr` входит в dword по `0x04`») и потому выглядел как результат
расследования. По правилу §40 KNOWN-ISSUES такие комментарии опаснее прямой
ошибки — их не перепроверяют.

**Что меняется в сборке.** Функция **вне** всех `#ifdef`, включая
`FULL_NOGEN2` (все `#if` в диапазоне строк 1000-5250 перечислены, охвата на
`find_pcie_cap` нет). Её результат используется для печати `GEN2C`
(`src/unlock_v2.c:5151,5167`) и в `xck`/`phase3`, которые вырезаны
`FULL_NOGEN2` в релизной сборке.

Следствие: **релизный `unlock_v3r` побайтово меняется** — в логе вместо
`GEN2C ... pcie_cap not found` печатается `cap@0x78 LNKCTL2=... TLS=...`.
По правилу проекта (`src/build.sh`, BUILDING §6.0) отпечаток нельзя фиксировать
до успешного прогона на железе, поэтому релизный md5 **оставлен прежним**, а
`out/flash-build.ps1` будет требовать `-AllowNewBuild`. Правка функционально
безопасна (в железо не пишет, путь анлока не меняет), но требует перепрошивки
и приёмки для обновления эталона.

#### Сборка и контроль, 2026-10-10

> ### ЭТАЛОННЫЙ КОМПИЛЯТОР ПРОЕКТА — **gcc-12**, НЕ `gcc` по умолчанию
>
> Подтверждено владельцем проекта 2026-10-10: все эталонные сборки делались
> на **gcc-12**. В WSL стоят обе версии: `gcc` -> 15.2.0, `gcc-12` -> 12.5.0.
>
> **`src/build.sh` переменной `CC` не знает** — строка 159 жёстко зовёт `gcc`,
> поэтому `CC=gcc-12 bash build.sh` молча собирает на **15.2.0**. Проверено и
> воспроизведено: `CC=gcc-12` дал md5, побайтово совпадающий с `gcc` (15).
> Подстановка работает только через шим в `PATH`:
>
> ```bash
> mkdir -p /tmp/shim
> printf '#!/bin/sh\nexec /usr/bin/gcc-12 "$@"\n' > /tmp/shim/gcc
> chmod +x /tmp/shim/gcc
> PATH="/tmp/shim:$PATH" BLOBS=... bash build.sh
> ```
>
> **Почему это видно по размеру.** Все четыре бинаря проекта — флешка
> `C68878AF`, `out/unlock_v3r_CMP70HX.efi`, сборка gcc-12 без правки и с
> правкой — имеют размер **680960** байт. Сборка на gcc-15 даёт **681984**,
> на 24576 байт больше:
>
> | компилятор | размер | совпадает с эталонными файлами проекта |
> |---|---|---|
> | **gcc-12.5.0** | **680960** | **да** |
> | gcc-15.2.0 | 681984 | нет |
>
> Значит зашитый в `build.sh` `DEE0BAAB / 657408` относится к **v3.15, тегу
> `rollback-2026-10-01`** — это другая, более старая сборка, и путать её с
> текущим релизом нельзя. **Текущий эталон — `C68878AF` (680960 байт)**: он же
> стоит в `out/flash-build.ps1:84` как `$REF_MD5` и в `README.md` как
> постоянный идентификатор загрузчика.

Собраны **две** версии эталонным компилятором, чтобы отделить влияние правки от
влияния тулчейна:

| сборка (gcc-12) | md5 | размер |
|---|---|---|
| `HEAD` без правки (контроль) | `003ff89dc8e736616cf83847ccd9c294` | 680960 |
| **с правкой `find_pcie_cap`** | **`3c076af7cf7c2bda65fda01f7678982c`** | 680960 |
| текущий эталон `REF_MD5` | `C68878AFAFD0D2D246D2E25C5ACBD888` | 680960 |

**Ни `HEAD`, ни новая сборка не совпадают с эталоном по md5.** Расхождение
большое: `cmp -l` даёт **330916** байт против загрузчика с флешки и 46568
байт против `out/unlock_v3r_CMP70HX.efi`. То есть дрейф исходников относительно
того, что лежит на носителе, **многократно больше** правки `find_pcie_cap`
(3 байта). Причина видна в списках строк: на флешке нет диагностических строк
`G2RCC canary precondition` и `G2RMS BAR0 SUSPECT/ALIVE`, которые появились в
§51.1-51.2. Флешка — сборка **v3.52 / release 1.0.0**, дерево ушло вперёд.

Поэтому эталон в `src/build.sh` **не тронут**: подставить непроверенное число
вместо непроверенного — тот же приём, который проект сам осудил в
`build.sh:722-726` («проверка была тождественно ложной и всё равно выглядела как
проверка»). Баннер печатает живой md5, и это правильный источник для сверки.

Для справки, замеры на gcc-15 (не эталонном) — из них видно, что правка
стабильна и от тулчейна не зависит:

| сборка (gcc-15, НЕ эталон) | md5 | размер |
|---|---|---|
| `HEAD` без правки | `49f4b425723c1383db2cd056deb90314` | 681984 |
| с правкой | `92efed10d9f331e6f5f04b6db1bc173d` | 681984 |

правкой**: оно есть и на чистом `HEAD`. Значит эталон `DEE0BAAB` был получен
при другой версии компилятора или других флагах, и в текущем окружении
недостижим. Это же отмечено в §8: gcc версии критичен (эталонные сборки

окружении, а подмена его непроверенным числом была бы тем же «тождественно
ложным» приёмом, который сам проект осудил в `build.sh:722-726`. Баннер
печатает живой md5, и это правильный источник для сверки.

### 4a.11.9 Прошивка 2026-10-10 — что обнаружилось на флешке

Прошивка выполнена штатным `out\flash-build.ps1 -AllowNewBuild`. Перед этим
`src\xfcc.efi` сохранён в `out\xfcc_E-G_4997ADC0.efi` — он оказался побайтово
идентичен `src/xfcc.efi`, то есть был в дереве и не пропал.

**1. На флешке лежал не релиз, а эксперимент E-G.**

```
md5 до прошивки : 4997ADC06D4FCA10DB01CE8D933B01D6  684544 байта
                 = src\xfcc.efi побайтово
VERSION.txt     : обещал C68878AF..., release 1.0.0
```

#### Новое расхождение: `width=0`

одним чтением, отдельной задачей.

### 4a.11.12 E-F: маска `0x88FE8` — ГИПОТЕЗА ОПРОВЕРГНУТА НА ЖЕЛЕЗЕ

Цель `xgate4` (`8917000`), стадия E-F. Она делает ровно недостающее из
предыдущего раздела: открывает `0x88FE8` прямо, MMIO, после гейта `0x8E1B0`,
и с readback. Проверяемая гипотеза: запись `TLS=2` на GPU отбрасывается
из-за маски домена `0x88xxx`.

```

**ГИПОТЕЗА ОПРОВЕРГНУТА.** Маска не открылась ни при какой из пяти попыток,
значит `TLS=2` на GPU отбрасывается **не** из-за неё. Шаг 1 после её открытия
дал ровно тот же `DROPPED`, что и до неё.

> **ПОПРАВКА 2026-10-10, ПОСЛЕ ЭТОГО ПРОГОНА. Вывод ниже был неполным, и
> ошибка — в пути доступа, а не в кремнии.**
>
> E-F писала `0x88FE8` обычным `mmio_write32` **с хоста**. Гейт `0x8E1B0`
> открывается **ботером**, и хост-MMIO в него после E-A не пишет — E-B заливает
> policy хостом и встаёт только потому, что ботер уже снял защиту. Для `0x88FE8`
> открывающего гейта у нас нет, поэтому хостовая запись была обречена
> **изначально**, и отрицательный результат ничего не говорил о домене.
>
> Косвенное доказательство, что маску открывает именно ботер, есть в коде:
> комментарий про маски фиксирует «`0x88fe8` откатился в `CF` после
> ResetSystem-Warm» (`src/unlock_v2.c`, блок про переживание FLR). Откатился
> **в `CF`** = до этого был `FFFFFFFF`. То есть адрес в проекте открывался,
> ботерной ROP-записью через `g_rj16[]`.
>
> Разбор продолжает E-G (`xgate5`): тот же адрес, но привилегированным
> выстрелом. Отрицательный результат E-F относится к хост-MMIO-пути и
> **не переносится** на ботerный.

**ЧТО ИЗ ЭТОГО СЛЕДУЕТ, А ЧТО НЕТ.** Не следует, что Gen2 недостижим, и
не следует, что рецепт референса неверен. Следует одно и узкое: хост-MMIO
путь к `0x88FE8` на нашем кремнии не работает. Ни о ботерном пути, ни о
свойствах домена этот прогон не говорит ничего.

**ПРО БОТЕРА В ЭТОМ ПРОГОНЕ — ОСТОРОЖНО.** В §4a.11.12 выше я сначала написал,
что «ботер отработал 242 раза и не открыл адрес». Это неверный вывод: все 242
упоминания `booter` в логе приходятся на рендер-стадию и E-A, а сама стадия
E-F ботер **не использовала**. Число упоминаний не равно числу выстрелов по
этому адресу — выстрела не было ни одного.

**ПОЧЕМУ ЭТО НЕ ПОВТОРЕНИЕ ПРОВАЛА РЕНДЕР-МАСОК.** Те адреса не открылись
ботером из-за лимита «два выстрела на бут-цикл» (§v3.19). Здесь ботер не
использовался вообще: запись шла прямым MMIO после открытия гейта, тем же
способом, каким E-B пишет policy set — и пять из пяти полей policy set встали
в этом же прогоне. Механизм рабочий, адрес всё равно закрыт. Это разные
причины, и вывод про лимит ботера сюда не переносится.

**НО И ОБРАТНОГО ВЫВОДА ТЕПЕРЬ НЕТ.** Из «хост-MMIO не берёт» не следует
«ботер не возьмёт» — это проверяется отдельно, и E-G (`xgate5`) именно это
и проверяет.

**ЗАМЕР, КОТОРЫЙ ЭТО ОПОРА.** `GEN2M after-unlock` в этом же прогоне:
`0x00823804` перешёл в `0xFFFFFFFF`, а `0x00088FE8` остался `0xFFFFFFCF`.
Анлок жив, адрес не тронут — ровно то, что предсказывает §4a.11.5.

| 7 | кик LTSSM **последним** | BAR0 `0x8872C = 6` |
| 8 | `TLS = 2` на GPU **и** на root port | PCI config `cap+0x30.w` |
| 9 | retrain | root port `+0x10.w \|= 0x20` |

**Важно, измерено ранее:** `LC2 TLS` через BAR0 (`0x880A8`) под живым GSP
**отбрасывается** — TLS ставится только через PCI config. §1p шаг 0.5, ошибка 2.

**Единственный честный критерий Gen2** — физическая полоса, а не
`nvidia-smi --query-gpu=pcie.link.gen.current` (это downshift в простое, §1p
шаг 0.1):

```
src/tools/pcie-bw.py  ->  > 5,5 GB/s     (против нынешних 3,343)
```

Gen3/Gen4 целью не является: `LINK_CAP` клампится кремнием, замер «write 03 →
readback 02» (`REGISTERS.md`), и на 40HX тот же барьер исследован до конца.

## 7. Приёмка

Строки ASCII в логе (`ulogf` транслитерирует всё вне `0x20..0x7E`, поэтому
кириллицы в логе нет):

```
XGATE phase0: gate 0x0008e1b0=0x........ ctrl 0x0008e1b4=0x........
XGATE phase1: target 0x0008e1b0 <- 0xffffffff gave 0x........ OPEN|NOT OPEN (polls=N, recheck=0x........, before=0x........)
XGATE phase2: control 0x0008e1b4 <- 0xffffffff gave 0x........ OPEN|NOT OPEN (polls=N)
XGATE VERDICT: OPEN | GATE-ONLY-LOCKED | INCONCLUSIVE
XGATE === E-A done: xg ===
```

`recheck` в фазе 1 отделяет «не встало» от «встало и слетело» (повторное
чтение через 0,5 с).

**Плюс обычная приёмка обязана сохраниться** (ничего не должно сломаться):

```
G2RMC render-masks top of iter 0: already open 0 of 2
G2RMC render-masks top of iter 1: already open 1 of 2
G2GFX step1-GFX_SEL ORDER A (GFX after SS): GFX_SPEED_SELECT=0x00000004 SET
END    ss0=0x88888888 ss1=0x00000008 PLM=0xFFFFFFFF
```

Отдельно: `pp512` / `tg16` не должны просесть (анлок ×11,25),
`×11.25` — проверка, что блок не сломал анлок.

## 10. Куда это ведёт

E-A — первый из трёх шагов нового плана. Он не самоцель, а **включатель**:

1. **E-A** (этот документ) — открывается ли гейт → оживает ли Gen2.
2. **Батчинг привилегированных записей.** Сейчас одна запись = один FLR +
   ботер = 1,24 с, поэтому рендер-цикл это 2 обязательные итерации (2 490 мс из
   4 894). Блоб 64 КБ использует **два** слова; если в ROP-хвосте есть вторая
   пара «значение/адрес», батчинг — это сдвиг указателей, а не исследование.
   Рецепт цепочки целиком (включая стек-пивот на второй стек, освобождение
   ACR-мьютекса и `booterCleanupAndHalt`) есть в исходниках:
   `Cyridd/cmpunlocker`, `0001-cmp40hx-unlock.patch` — та же конструкция
   canary-ROP, тот же блоб, слоты в той же области `0xF9xx`.
3. **Host2Jtag — закрыто замером, см. §4a.9.** На GA104 окно `0xC8xx` пусто;
   признака запертых гейтов нет ни в нём, ни в `0xC0xxx`. Трек B неприменим
   к этой карте. Осторожность оправдалась: перенос `0xC840` вслепую не дал бы
   ничего.

Детали и обоснование — в разделе плана, обсуждавшемся 2026-10-09.

## 11. Что E-A НЕ делает

* Не трогает линк, TLS, ретрейн, политику PCIe — ни одного функционального бита.
* Не меняет релизную сборку (доказано побайтово, §8).
* Не включает свип `g_rj16` целиком — из-за ловушки с `done`, §3.1.
* Не трогает VBIOS и не прошивает ничего.
* Не претендует на Gen3/Gen4 — там кремниевый кламп, измерено.

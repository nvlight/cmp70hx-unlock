# 🎮 Разблокировка CMP 70HX

Полная разблокировка вычислительной и графической мочи **NVIDIA CMP 70HX** (GA104, 8 ГБ, PCI ID `10de:248a`) в Windows — с помощью обычной флешки, EFI-загрузчика и **без перезагрузок**.

Анлок выполняется **до загрузки ОС**, поэтому Windows просто стартует с уже полностью открытой картой.



> ℹ️ **О приведённом коде.** Исходники начинали с CMP 90HX. Этот порт
> нацелен на **CMP 70HX**, и это единственная цель сборки: переменной `TARGET`
> больше нет, оригинальный 90HX под собственный бинарник не собирается
> (история — в `git log` и PORT-STATUS §1). Всё, что зависит от карты, лежит
> в одном блоке `TARGET PROFILE` в начале `src/unlock_v2.c` и **выводится**
> из размера кадрового буфера. Что подтверждено на железе, а что
> экстраполировано — в [KNOWN-ISSUES.md](KNOWN-ISSUES.md) §13–16.

## Что такое CMP 70HX?

Карта — кристалл семейства GA10x, который NVIDIA продавала как **«только для майнинга»**. Прошивка урезает карту: производительность составляет малую долю реальной. Залоченная карта выдаёт ~230 t/s в llama-bench; разлоченная 90HX — **~3700 t/s** (в 16 раз больше).

> Проект собирает **только CMP 70HX**. 90HX упоминается здесь как база для
> сравнения (с неё начинали исходники и от неё считается прирост), а не как
> поддерживаемая цель сборки — см. KNOWN-ISSUES §49–50.

Этот проект возвращает кристаллу всю вычислительную мощь: EFI-приложение запускается с загрузочной флешки ещё до загрузки ОС. **Проект открыт** — исходники в [`src/`](src/), сборка описана в [BUILDING.md](BUILDING.md).

**Что именно разблокировано на 70HX** ([подробно, п. 1k](docs/70HX-PORT-STATUS.md)):

| | состояние |
|---|---|
| вычисления | **разблокированы**, ×11,25 по `pp512` |
| механизм блокировки | **потолок issue-rate 1/32** на FP32 и DP4A, снят полностью |
| периферийные issue-rate | **на 91–99,8 % от архитектурного пика**, остаточных лимитов нет |
| частота | 1545 MHz под нагрузкой, троттлинга нет, потолком не является |
| ядра | 3840 CUDA core из 6144; **A/B сделан — анлок это число не меняет** |
| графика | **разблокирована частично**: `GFX_SPEED_SELECT = 0x4`, Cyberpunk 2077 **50 fps / 135 Вт**. `FEAT_READOUT_0` бит 8 (PGRAPH) остаётся 0 — это урезанный кристалл, а не не открытая маска |

Ключевой результат A/B: заблокированная карта отдаёт ровно **1/32** от
пика на FP32 и DP4A (3,99 из 128, 2,00 из 64), при этом FP16, BF16 и
INT32 не ограничены никогда. То есть блокировка — это потолок выдачи
команд, а не отключение ядер, и наш анлок снимает его целиком.

Это класс «только вычислительные ограничения». У эталонной
разблокированной **CMP 50HX** (GA107) на патчах от dartraiden снята и
графика полностью — 230 Вт под нагрузкой, 3D играет, LLM быстрый. По
графике 50HX уходит вперёд, и разрыв объясняется размером кристалла, а не
недостающей разблокировкой (PORT-STATUS §8).

## Как работает анлок

1. **Предзагрузка.** Загрузчик Windows (`bootmgfw.efi`) читается в ОЗУ через сырой блочный ввод-вывод собственным FAT32-парсером. (UEFI SimpleFileSystem не используется — на некоторых платах AMI он вешает систему.)
2. **Анлок.** Приложение проводит SEC2 (Falcon) видеокарты через её защищённую загрузку:
   - снимает защиту записи памяти (WPR2),
   - загружает подписанный «канареечный» пейлоад (V67) в ботер SEC2,
   - открывает защищённый режим GPU (PLM),
   - прописывает compute-селекторы (SS0/SS1) и маски рендера.
3. **Ресет.** Function Level Reset (FLR) сбрасывает защёлкнутые регистры защиты — селекторы его переживают.
4. **Загрузка.** Приложение возвращается в прошивку без POST, и Windows грузится с уже разлоченной картой. **Перезагрузки нет** — POST сбросил бы анлок.

Сам эксплойт: подписанный ботер SEC2 содержит баг stack-canary (Jon Pry, *"A Canary in the Crypto Mine"*). При проверке нашего увеличенного 64-КБ «подписанта» исполнение уходит в ROP-цепочку, которая выполняет произвольные привилегированные записи в регистры — включая открытие PLM.

## Время загрузки

Полный прогон EFI на 70HX — **≈ 16 с**. Было **3 мин 40 с** (218,1 с), то есть
**в 13,6 раза быстрее**.

| | |
|---|---|
| измеренный диапазон последних прогонов | 15 303…15 964 мс |
| **публикуемая оценка** | **≈ 16 с** |
| разброс прогона | ±200…660 мс |
| лучший одиночный замер | 15 303 мс (v3.38) — **занижен**, в нём аномалия |

**Почему не публикуем 15,3 с.** Разброс между прогонами (±200…660 мс)
превышает размер почти всех оставшихся рычагов. Лучший одиночный замер
содержит известную аномалию: `render: FLR settle` дала в нём 474 мс на итерацию
вместо нормальных 499,3. Число не должно быть лучше измеренного.

Первоисточник с разбором каждого этапа — **[out/BUILDS.md](out/BUILDS.md)**.

### Почему 14 с у xrip недостижимы настройкой констант

Тот же класс разблокировки на CMP 50HX у
[xrip](https://github.com/xrip/cmp50hx-unlock/tree/master/efi-unlock-windows)
укладывается в 14 с.

Рендер-цикл у нас — **8 масок, и на каждую свой обязательный цикл FLR + booter**
то есть ≈10,0 с из 16; период итерации **≈1,24 с**, измеренный по меткам времени
в логе (`t=5417…6671…7912…` мс, восемь точек `render: FLR settle`, период
1237…1254 мс), а **не** сложенный из счётчиков стадий: сами `TIME MK` вложены
друг в друга, их сумма (20,1 с) больше длительности прогона, о чём лог
предупреждает отдельной строкой (`TIME … SUM is NOT a phase total`). Это **измерено, а не предположено**: между
итерациями печатается, сколько масок уже открыто, и оно равно номеру итерации
на всех восьми:

```
iter 0: already open 0 of 8      iter 4: already open 4 of 8
iter 1: already open 1 of 8      iter 5: already open 5 of 8
iter 2: already open 2 of 8      iter 6: already open 6 of 8
iter 3: already open 3 of 8      iter 7: already open 7 of 8
```

Каждый цикл открывает **ровно одну** маску, поэтому батчить нельзя: сократить
число циклов, не меняя подход, невозможно. Выйти на 14 с можно только
переписыванием способа анлока, а не подбором констант.

Причина и план сокращения: **[PLAN-SPEED.md](PLAN-SPEED.md)**. Разбор
отвергнутых попыток и почему три из них дали регрессию —
**часть II «Ретроспектива v3.16»** того же файла.

## Приёмка сборки — что должно быть в логе

Лог читается хостовым `out\read-log.ps1` (сырые секторы флешки, не serial).
Проверяется **внутри бинарника** до записи на флешку — BUILDING §6.1.

Сборка принята, если в логе есть **все** эти строки:

Лог пишется `ulogf()`, который транслитерирует всё вне `0x20..0x7E` в `?`
(`docs/LOGGING.md` §3), поэтому в нём **нет кириллицы** — искомые строки
ASCII. Приводим устойчивые фрагменты (точные строки длиннее и меняются от
сборки к сборке; `out/verify-log.ps1` проверяет их на соответствие):

```
G2RMS  render-masks TOTAL: XVE window open 8 of 8 | 0x823800=0xFFFFFFFF
G2GFX  step1-GFX_SEL ORDER A (GFX after SS): GFX_SPEED_SELECT=0x00000004 SET
G2SUM  ... readback 0x00000004 OK
END    ss0=0x88888888 ss1=0x00000008 PLM=0xFFFFFFFF
END    ---- end of log ----
```

И **ни одной** из этих:

| Плохая строка | Что означает |
|---|---|
| `XVE window open` < 8 | рендер-разблокировка сломалась |
| `dbg=0x007E0009` | ядро стартует и гибнет, DMA не доставила |
| `FLRX  WPR2 restored … *** DID NOT HOLD ***` | ботер не защёлкнул WPR2 (строка `FLRX`, а не `G2RMS`/`END`) |
| отсутствие маркера `END` | лог оборвался; обрыв на границе сектора = не сброшен последний буфер |

> **Про `*** UNEXPECTED ***` на WPR2 — это не брак.** В строках `G2RMS … TOTAL`
> и `END` штатно печатается `WPR2=0x01EAD000/0x01F7EE00`: `WPR2_LO` в финале
> читается со сдвигом `0xD1000` от `0x01F7E000`, тогда как ожидаемое значение
> `0x01F7E000` встаёт корректно в середине цикла (`WAIT *** WPR2 ESTABLISHED
> … after 11 ms ***`). Состояние разобрано и **не является помехой** анлоку —
> см. `KNOWN-ISSUES.md` §42.10 и `docs/70HX-PORT-STATUS.md` §9. Признаком
> брака считайте `UNEXPECTED` в строке `FLRX`, а не в финальных.

Отдельно сверяется **время прогона** — строка `TIME t=…ms final: before return
to firmware` плюс замер секундомером. Расхождение больше 5 с означает, что
часть работы не попала в счётчик.

## Требования

- NVIDIA CMP 70HX (PCI ID `10de:248a`)
- Материнская плата UEFI с boot-меню (F12)
- Windows на GPT-диске с EFI-разделом
- **Secure Boot выключен** (загрузчик не подписан)
- Флешка (≥ 256 МБ)
- Образ `gsp_ga10x.bin` из пакета драйвера NVIDIA **610.43.03** на флешке
  рядом с `BOOTX64.EFI`

## Установка

1. Скачайте последний образ со страницы [Releases](https://github.com/WildFlash1st/cmp90hx-unlock-for-windows/releases).
2. Запишите образ на флешку через [Balena Etcher](https://etcher.balena.io/), [Rufus](https://rufus.ie/) (режим DD) или `dd`:
   ```bash
   dd if=<образ>.img of=/dev/sdX bs=4M status=progress
   ```
   ⚠️ Перепроверьте имя устройства — команда стирает всё на флешке!
3. Сверьте md5 со значением из описания релиза.
4. Перезагрузитесь, нажмите **F12** (или клавишу boot-меню вашей платы), выберите флешку.
5. Анлок выполнится автоматически — Windows загрузится на полной мощности. Нажимать ничего не нужно.
6. *(Только для рендера/игр)* Установите патченный драйвер из [NVIDIA-patcher](https://github.com/dartraiden/NVIDIA-patcher).

### Повторный запуск после перезагрузки

Анлок **волатилен**: полный ребут (POST) сбрасывает GPU. Чтобы разблокировать снова — просто загрузитесь с флешки ещё раз и дайте ей передать управление Windows. Всё.

## Сборка из исходников

```bash
git clone https://github.com/WildFlash1st/cmp90hx-unlock-for-windows
cd cmp90hx-unlock-for-windows/src
BLOBS=/путь/к/блобам bash build.sh   # единственная цель: CMP 70HX / GA104
```

Результат — один файл `unlock_v3r.efi`. Он же прошивается и он же является
откатом; якорь отката — git-тег `rollback-2026-10-01`, то есть откат равен
пересборке из исходников на этом теге (см. KNOWN-ISSUES §50).

**Два разных md5 — и это нормально.** Сборка из тега и сборка из HEAD дают
разные бинарники, поэтому сверять надо с тем, что именно вы собираете:

| что собираем | md5 | размер |
|---|---|---|
| `git checkout rollback-2026-10-01 && bash build.sh` | `DEE0BAAB1B7C222399C091EAD15D071B` | 657408 |
| HEAD (v3.39) | `67F7B5A84F8EFEBA5A4718004B0589ED` | 671744 |

**Несовпадение md5 — не признак подмены.** Оно означает лишь, что вы собрали не
тот checkout. Если нужен откат, пересоберите **из тега** и получите `DEE0BAAB`;
если собираете HEAD — сверяйтесь с реестром сборок в
[out/BUILDS.md](out/BUILDS.md), а не с якорем. Никогда не делайте
`git checkout -B good`, чтобы «сохранить расхождение»: это закрепляет
непроверяемое состояние ([BUILDING.md](BUILDING.md) §6.0, `src/build.sh`).

Пререквизиты, происхождение блобов и рецепт USB-образа — в **[BUILDING.md](BUILDING.md)**; известные ограничения и нерешённые проблемы — в **[KNOWN-ISSUES.md](KNOWN-ISSUES.md)**.

> 🔁 **[BUILDING.md §6](BUILDING.md)** — обязательный порядок цикла «сборка → флешка → лог»: после любой правки исходников загрузчик перезаписывается на флешку и проверяется по содержимому, а после каждой загрузки лог снимается и разбирается. Оба шага выполняются **без вопроса пользователю**. Перезагрузка и F12 остаются за человеком.

### Как убедиться, что прошит правильный образ

Баннер на экране всегда печатает профиль карты. Строка вида

```
=== NVIDIA CMP 70HX (GA104) Unlock — PCI 10de:248A, FB 0x200000000 (8192 MB) ===
=== FRTS=0x1F7E00000 (0x1F7E00 pages)  WPR2=0x01F7E000/0x01F7EE00  FWSEC=fwsec_ga104.bin ===
```

Значения FRTS/WPR2 — из прогона 2026-09-29. Прежние `0x1FFE00000` /
`0x01FFE000/0x01FFEE00` относились к старой формуле и разошлись с тем, что
реально лежит в `DMEM_MAPPER_V3` карты. Точные значения для вашей карты
всегда есть в первой строке лога: `CMPUNLOG v1 … frts=0x… wpr2=0x…/0x…`.

должна совпасть с вашей картой. Если карта не найдена, приложение перечислит
все видимые `10de:xxxx` — значит у вашего экземпляра другой Device ID, и его
надо вписать в `TARGET_PCI_DEV` (см. [KNOWN-ISSUES.md](KNOWN-ISSUES.md) §13).

## Структура репозитория

- `src/unlock_v2.c` — всё EFI-приложение (единственная сборка собирается из него);
  блок `TARGET PROFILE` в начале файла — единственное место с константами карты
- `src/build.sh` — скрипт сборки (gnu-efi, одна цель: CMP 70HX); `src/tools/` — хелперы извлечения прошивок
- `docs/` — грабли платформы, заметки по регистрам, отчёт диагностики Code 43, процедура патча блобов
- `docs/70HX-FINAL-SUMMARY.md` — **итог работы по 70HX**: что доказано, что опровергнуто, что осталось
- `docs/70HX-PORT-STATUS.md` — **статус порта 70HX**: что работает, что нет, разбор блокера `WPR2`
- `docs/70HX-VBIOS-ANALYSIS.md` — **разбор VBIOS карты 70HX**: подписи FWSEC, структура `DMEM_MAPPER_V3`
- `docs/70HX-NEXT-STEPS.md` — **план дальнейших шагов** с критериями успеха каждого эксперимента
  ⚠️ в основном исторический, написан до анлока compute и графики
- `docs/70HX-DRIVER-ANALYSIS.md` — **разбор драйвера 610.43.03**: подтверждение формул и найденная `WPR_END_MARGIN`
- `docs/GOTCHAS.md` — **грабли платформы**: MBR/ESP, vfio, EFI-подвески, PCIe Gen2
- `docs/REGISTERS.md` — **карта регистров**: что открываем, чем, и что подтверждено на 70HX
- `docs/FLASH-AND-LOG.md` — **процедура**: запись загрузчика на флешку, проверка, снятие лога
- `docs/LOGGING.md` — **механика логирования**: формат на диске, путь записи в `unlock_v2.c`, путь чтения в `out/read-log.ps1`, контракт синхронности между ними, диагностика отказов

- `BUILDING.md` — сборка из исходников, блобы, цикл «сборка → флешка → лог»
- `vendor/` — **сторонние материалы** (переведённый README xrip/cmp50hx-unlock про CMP 50HX).
